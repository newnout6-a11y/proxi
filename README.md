# Retool AI relay (OpenAI / Anthropic compatible)

Локальный HTTP-relay над прямым протоколом Retool AI (`POST /api/gpt/copilotStreamGPT`)
с поддержкой prompt caching и нативных клиентских инструментов.
Даёт доступ к моделям, доступным вашей организации Retool, из обычных OpenAI- и
Anthropic-клиентов (Codex, opencode, Aider, Continue, Claude Code, curl).

Честная рамка: это адаптер к внутреннему протоколу, а не официальный API Retool.
Совместимость ограничена списком ниже.

## Возможности

- POST /v1/chat/completions — OpenAI Chat Completions, streaming и non-streaming.
- POST /v1/responses — OpenAI Responses API (streaming и non-streaming).
- POST /v1/messages — Anthropic Messages API (streaming и non-streaming, x-api-key).
- GET /v1/models — каталог моделей с capabilities и размером контекста.
- GET /v1/balance, GET /v1/usage (суммы по всем аккаунтам и разбивка `accounts[]`),
  GET /health (200, если есть хотя бы один доступный для запросов аккаунт со свежим
  балансом; иначе 503).
- Обязательный локальный ключ relay: Authorization: Bearer, x-api-key или ?key=.
- Изоляция: один тред на один диалог; OpenCode affinity (`x-session-affinity`/`X-Session-Id`)
  разделяет диалоги, а tool-result ходы остаются в том же треде.
- Локальное выполнение команд (<exec_command>) с allowlist, чистым окружением
  и убийством дерева процессов по таймауту.
- Инжект контекста проекта с redaction секретов.
- Учёт кредитов по каждому ходу, credits_used в usage, история в /v1/usage.
- Фоновое продление сессии Retool каждые 15 минут, сохранение cookies после
  ротации и общий повтор при 401/403 для моделей, истории сообщений и баланса.
- Прямой транспорт (direct): быстрый streaming через POST /api/gpt/copilotStreamGPT
  с кэшируемым system-блоком (prompt caching с чтением десятков тысяч токенов
  из KV-кэша Retool) и нативной поддержкой клиентских инструментов. Первый токен —
  около 1.5–2 секунд вместе с контекстом. Устаревший WebSocket sandbox-путь отключён.
  Замеры — [docs/direct-transport.md](docs/direct-transport.md).
- Управление системным промптом без перезапуска: файл `prompts.json` с профилями и правилами
  (по клиенту, модели, назначению запроса и заголовку), правки system клиента, истории и описаний
  tools, предпросмотр итогового промпта и просмотр того, что увидела модель. Без файла поведение
  прежнее. Руководство — [docs/prompt-control.md](docs/prompt-control.md).

## Установка

Нужен Python 3.11 или новее (relay использует `asyncio.create_task(..., context=...)`).
CI проверяет Python 3.14.

    python -m pip install -r requirements.txt
    copy config.example.json config.json     # заполнить base/page_uuid/cookie/xsrf/workspace_root
    python proxy.py                          # ключ сам появится в relay_key.txt

`requirements.txt` ставит и `regex`: этот модуль исполняет регулярные выражения `prompts.json` с таймаутом
на операцию. Без него relay запускается, но документ промптов с регулярным выражением не принимается.

Фоновый запуск, переживающий закрытие терминала и перезапускающийся при падении:

    Start-Process pwsh -ArgumentList '-NoProfile','-File','scripts\run_relay.ps1' -WindowStyle Hidden -PassThru |
        ForEach-Object { $_.Id | Out-File relay.pid }
    taskkill /PID (Get-Content relay.pid) /T /F     # остановить (супервизор перезапустит — убивать с /T)

Супервизор не запускает relay, пока порт из конфига (`port`, `RELAY_PORT`) уже кто-то слушает: второй
супервизор (строка запуска выполнена повторно), relay в терминале или другая программа. Тогда он пишет в
`relay.log` строку `supervisor: port … is already in use` и завершается. Relay, вышедший раньше чем через
30 с после запуска, считается незапустившимся: следующий запуск ждёт вдвое дольше (2, 4, 8 … с, не больше
5 минут), а после восьми таких выходов подряд супервизор останавливается строкой
`supervisor: the relay exited within 30 s …`; причина — в строках `relay.log` над ней. Порог и число
задают параметры `-FastExitSeconds` и `-MaxFastExits`.

При прямом запуске `Ctrl+C` один раз начинает завершение: relay закрывает приём
новых запросов, отменяет активные ходы и дожидается очистки keepwarm в его event
loop. Повторные сигналы не запускают дополнительные процедуры shutdown.
Зависший HTTP-worker, ещё ожидающий первые заголовки, не удерживает процесс
после ограниченной по времени очистки; завершённая часть расхода учитывается,
а отсутствие отчёта upstream остаётся неизвестным расходом.

Если RELAY_API_KEY и relay_api_key не заданы, ключ генерируется в relay_key.txt
и печатается в баннере маскированно.

Секреты можно держать вне файла: RETOOL_COOKIE, RETOOL_XSRF, RETOOL_BASE,
RETOOL_PAGE_UUID, RETOOL_THREAD_ID, RELAY_API_KEY. Для OpenCode affinity приходит
в `x-session-affinity`/`X-Session-Id`; config.json и cookies.txt в .gitignore.

Сессия продлевается через `/api/refreshtoken` при запуске и затем каждые
`session_refresh_interval` секунд (по умолчанию 900). Новые cookie и xsrf
атомарно сохраняются в исходный `config.json`, остальные настройки остаются
на месте. Файл переписывается только при реальном изменении cookie или xsrf (или когда
нужно вернуть потерянный `account_id`): продление без ротации его не трогает, поэтому
пять аккаунтов не дают десятков лишних записей в час. В журнале у успешного `auth.refresh`
`rotated` означает, что cookie или xsrf изменились, а `persisted` — что `config.json`
был переписан. После перезапуска используется последняя сохранённая сессия.
При ошибках продление повторяется с паузой от 20 секунд до 5 минут;
параллельные клиенты используют одно обновление. `0` отключает фоновое продление.

Для секретов из `RETOOL_COOKIE`/`RETOOL_XSRF` обновление работает в памяти:
значения окружения не записываются в конфигурацию. Если выполнен новый вход
и обновлён `config.json`, работающий relay подхватит его при следующем продлении
или ошибке авторизации. Истёкшую или отозванную сервером сессию без действующих
учётных данных `/api/refreshtoken` восстановить не может — нужен новый вход.
`/health` показывает только сводку сессии обслуживающего аккаунта (`session`: признак
фонового продления, время последнего успеха, ошибка сохранения) и число аккаунтов
по состояниям (`accounts`: `total`, `routable`, `states`; аккаунт в паузе после часового
лимита Retool — состояние `rate_limited`, а `rate_limited_until` показывает ближайшее
возвращение). Подробное состояние
продления каждого аккаунта диспетчера (`auth_failures`, причина исключения) в
`/health` не выводится: смотрите `accounts[]` в `GET /v1/balance` и журнал.
`/health` отвечает `200`, если есть хотя бы один доступный для запросов аккаунт со
свежим балансом; устаревший кэш баланса означает `503`, а не успешную проверку upstream.

Обслуживающий аккаунт для `session` — первый доступный для запросов, иначе первый включённый,
иначе первый в списке: первый аккаунт в `config.json` может быть выключен. Поле `models` —
число опубликованных моделей (то же, что в `/v1/models`), а не размер реестра.

При первой загрузке каждому `accounts[]` назначается и сохраняется уникальный
`account_id`. Обновление ищет точный ID с проверкой tenant; одинаковые страницы
не объединяют аккаунты. Запись, потерявшая `account_id` (например, после внешнего
входа, переписавшего `config.json`), принимается только при однозначном совпадении
`base` + `page_uuid`; ID дописывается обратно. Запись настроек и ротаций использует
общую межпроцессную блокировку, а продление одного ID в одном файле выполняется
одним владельцем. Ресурс другого tenant не наследуется из глобальных настроек.
Новые диалоги выбирают аккаунт с маршрутом нужной модели; параллельный запрос
существующего диалога использует тот же аккаунт.

`config.load()` не только читает файл: при первом запуске он один раз дописывает
сгенерированный `account_id` в `config.json` (файл при этом переформатируется с
отступом 2) и создаёт рядом служебные файлы блокировок `*.lock`/`*.auth-*.lock`
(они в `.gitignore`). Чтобы относительно этого ничего не менять на диске, задайте
секреты через `RETOOL_COOKIE`/`RETOOL_XSRF` (тогда запись отключена) или сделайте
`config.json` доступным только для чтения: relay не упадёт, оставит сгенерированные
ID в памяти и выведет предупреждение в stderr. Отсутствующий конфиг даёт понятную
ошибку без лишнего `.lock`.

Привязка диалога к аккаунту сохраняется, пока аккаунт доступен и имеет маршрут к
запрошенной модели: дочерний или служебный запрос диалога остаётся на нём. Если
аккаунт исчерпан, упёрся в часовой лимит Retool, требует нового входа или не имеет
маршрута к модели, диалог переносится на другой аккаунт (подписанные блоки остаются на
старом, и префикс записывается заново; кэш провайдера общий для аккаунтов, см.
`account_move_keeps_history`). Если подходящего аккаунта нет вовсе, relay возвращает 503 (нет
маршрута), 402 (баланс) или 429 с `Retry-After` (часовой лимит Retool).
Привязка переживает перезапуск relay: она хранится по `account_id` (не по cookie) вместе
с состоянием диалога и действует на тех же условиях, что у живого диалога
(см. «Состояние диалогов после перезапуска»).

«Нет маршрута» бывает двух видов. Если ни один аккаунт не может обслужить модель по
настройке (снята провайдером, нужен BYOK или retention, нет ресурса провайдера),
ответ — постоянная 404 `not_found_error` с причиной; для stream это настоящий HTTP 404
до начала потока, а не событие внутри `200`. 503 остаётся для «сейчас нет пригодного
аккаунта»: все выключены, единственный способный обслужить модель выключен или нужен
новый вход.

«Ни один аккаунт» считается по аккаунтам, на которых этот запрос может выполниться, и
один и тот же список читают каталог `/v1/models`, проверка 404 до начала потока и
выбор аккаунта. В режиме `session_mode: shared` запрос с инструментами идёт в общую
сессию, которую обслуживает только первый аккаунт (у него нет ресурса — настоящая 404,
даже если он есть у второго); запрос без инструментов (текстовый диалог, служебные
вызовы клиента) может уйти на любой аккаунт. Исключение — пул, в котором ни у одного
аккаунта (включая выключенные и не обслуживающие этот запрос) нет ни одного ресурса
провайдера: каталог показывает его целиком, а причину «нет ресурса» называет сам запрос.

Продлением и балансом всех аккаунтов управляет один диспетчер (`accounts.py`):

- первые проверки разнесены на 2 с между аккаунтами, одновременно идёт не больше
  `account_refresh_parallel` (3) проверок, интервалы получают случайный сдвиг ±10%;
- общую паузу для всех аккаунтов (20 с → 5 мин, а не N повторов) ставят только
  сбои сети. Ошибки Retool 5xx и локальные сбои дают backoff только этого аккаунта,
  остальные продолжают продлеваться и не считаются выходом из аккаунта;
- после трёх отказов продления подряд (401/403 или ответ Retool «renewal rejected»)
  аккаунт исключается из пула (`нужен новый вход` в консоли и журнале) и возвращается
  после успешного продления. Если других аккаунтов нет, он остаётся запасным: 401
  перечитывает `config.json`;
- баланс каждого аккаунта запрашивается раз в `account_balance_interval` (300 с;
  `0` — раз в час). Аккаунт с подтверждённым балансом ниже `min_account_balance` (20)
  выбирается для новых запросов в последнюю очередь: порог — это резерв failover,
  а не запрет. Если ни один аккаунт не выше порога, обслуживается самый богатый из
  доступных с балансом больше 0 (или ещё неизвестным): последние кредиты тратятся
  до нуля, это относится и к единственному аккаунту. Локальное списание ниже порога
  сразу вызывает проверку баланса на сервере;
- если запрос упал до первого байта ответа (402/`insufficient_credits` или 5xx,
  кроме таймаутов) и проверка баланса подтвердила нехватку, аккаунт исключается, а
  запрос повторяется на другом. Диалог переезжает целиком, и новый аккаунт один раз
  заново записывает кэш префикса. Принудительная проверка баланса не чаще раза в 15 с
  на аккаунт: параллельные запросы делят результат уже идущей проверки, а в пределах
  15 с может быть использован результат предыдущей;
- клиент получает 402 `insufficient_credits` («Баланс Retool закончился», балансы
  аккаунтов) только когда подтверждённый баланс всех подходящих аккаунтов не больше 0
  или все они исключены failover'ом. Статус всегда 402; 429 остаётся лимитом запросов;
- Retool ограничивает managed-ключи лимитом на организацию в час и отвечает 429 с
  текстом «hourly limit of managed API key usage» (без учёта регистра; обычный
  короткий 429 так не считается). Это лимит аккаунта, а не запроса: аккаунт получает
  состояние `rate_limited` и выходит из пула до `rate_limited_until` (журнал
  `account.rate_limited`, поле в `/health`, `GET /v1/balance` и админке). Если клиенту
  ещё ничего не отправлено и бюджет попыток не исчерпан, ход сразу повторяется на
  другом аккаунте (`account.failover` с кодом ошибки). Ошибку посреди ответа повторить
  нельзя, но аккаунт всё равно исключается, и следующий запрос уходит на другой.
  Привязанные диалоги переезжают сами при следующем запросе, не возвращаясь назад
  после паузы; при переезде подписанные блоки рассуждений не переносятся (см. «Привязка
  диалога» выше), а кэш провайдера общий для аккаунтов: префикс, записанный на одном,
  прочитан целиком на другом (12 пар диалогов из 12, 2026-11-07), и заново пишется он из-за
  потерянных подписей (настройка `account_move_keeps_history` берёт их с собой). Переезд дорог: 78 852 токена записи и 38 с до
  первого токена (a5, `ddd7b74f`), у большого диалога Codex на Opus 489 786 токенов
  (`8f8d8567`). Поэтому есть настройка `account_rate_limit_wait` (секунды, 0 по умолчанию —
  переезжать сразу): запрос диалога с префиксом не меньше 8000 токенов один раз ждёт на
  этом аккаунте, не исключая и не паркуя его (журнал `account.rate_limit_wait`), и спрашивает
  его ещё раз; если лимит снят, диалог остаётся с историей и кэшем
  (`account.rate_limit_lifted`), если нет — всё идёт, как описано выше. Ждать столько, сколько
  прислал Retool в `Retry-After`, если это не больше настройки; без заголовка (так отвечает
  Retool сейчас) — всё значение. Новый диалог и диалог с малым префиксом не ждут. Сколько
  держится лимит, неизвестно: после включения `account.rate_limit_lifted` покажет, снимается
  ли он за выбранное время;
- Retool не присылает `Retry-After`, поэтому пауза — `account_rate_limit_cooldown`
  (900 с); заголовок, если появится, имеет приоритет (не больше часа), берётся как есть
  и в лестницу повторов не входит. Лимит у Retool скользящий: аккаунт, снова упёршийся
  раньше, чем продержался столько, сколько был в паузе, получает паузу на 5 минут длиннее
  (15 → 20 мин, потолок — большее из `account_rate_limit_cooldown` и 20 минут). Если
  аккаунт продержался дольше последней паузы, отсчёт начинается заново с
  `account_rate_limit_cooldown`. Первый настоящий запрос после паузы служит пробой:
  новый 429 снова исключает аккаунт с большей паузой, а клиент этого не замечает. 429
  запроса, ушедшего до последнего возврата аккаунта (он стартовал ещё до паузы), —
  устаревшая весть: он не исключает аккаунт заново и не удлиняет паузу, а сам запрос
  уходит на другой аккаунт. Аккаунт возвращается сам при ближайшем тике диспетчера
  (`account.available`) и никогда не берётся как резерв `min_account_balance`, даже с
  положительным балансом. Когда в паузе все подходящие
  аккаунты, клиент получает 429 `rate_limit_error` с `Retry-After` до ближайшего
  возвращения и текстом «все аккаунты упёрлись в часовой лимит Retool». Для запросов
  со `stream: true` relay проверяет это до начала потока: тот же 429 с `Retry-After`,
  а также 402 (все исчерпаны) и 503 (все выключены) приходят настоящим HTTP-статусом,
  а не событием внутри `200`. Проверка только читает состояние аккаунтов, ничего не
  резервирует и смотрит на те же аккаунты, что и выбор сессии (диалог, чей аккаунт
  недоступен, переезжает на любой пригодный); перед 402 она один раз перепроверяет
  балансы исключённых аккаунтов, как и сам ход. Если аккаунт выбыл между проверкой и
  выбором сессии, остаётся событие ошибки в потоке. Пауза хранится в памяти: после
  перезапуска первый запрос к аккаунту, который ещё в лимите, снова получит 429 и
  повторится на другом.

Пустой ответ upstream сам по себе не считается нехваткой баланса. `GET /v1/balance`
показывает сумму известных балансов и состояние каждого аккаунта в поле `accounts`;
если баланс части аккаунтов неизвестен, `available` и `monthly_allocation` покрывают
только известные: `partial: true`, `unknown_accounts` — число пропущенных, `accounts_total` —
всего. Стартовая строка `balance: X / Y` в таком случае заканчивается пометкой
`(partial: 1 of 5 accounts unknown)`. Месячный лимит, которого нет в ответе Retool (или он
`null`), считается неизвестным, а не нулевым: у такого аккаунта `monthly_allocation: null`
и `used_month: null`, сумма по пулу помечена `partial: true` (пометка в стартовой строке —
`(partial: monthly allocation unknown for some accounts)`, а сам лимит в ней `?`). Явный
`0` в ответе остаётся настоящим нулём. Балансы для `/v1/balance`, `/health`, админки и
стартовой строки запрашиваются у аккаунтов параллельно, до 8 одновременно; этот предел
отдельный и от `account_refresh_parallel` (фоновые проверки диспетчера) не зависит.
`GET /v1/usage` суммирует расходы всех аккаунтов (`accounts[]` — по каждому).

Повтор пустого ответа зависит от слоя. Orchestrator не повторяет пустой ход для
клиентских текстовых вызовов (`client-text`, а также Auto mode, заголовки, пробы).
Прямой транспорт повторяет пустой ответ `upstream_empty_retries` раз (по умолчанию 1)
для всех запросов, кроме `auto-mode-check`, `session-title` и `connection-probe`: эти
три не повторяются никогда (тот же запрос детерминированно даёт тот же пустой ответ),
остальные — включая `client-text` — повторяются за деньги. За один запуск relay
сохраняется не более одного тела пустого ответа на каждую пару «тип запроса + модель»
в `<state-dir>/logs/upstream-400/` со статусом `empty`; число хранимых комплектов
ограничено `upstream_error_max_dumps`.

Если сессия продлилась на пути запроса или внешним входом в `config.json`
(новые cookie подхвачены), аккаунт возвращается в пул при ближайшем тике
диспетчера (около секунды), без ожидания планового продления. Перед ответом 402 relay
один раз перепроверяет балансы исключённых аккаунтов, так что пополнение подхватывается
без ожидания таймера.

## Использование

    curl.exe http://127.0.0.1:8787/v1/chat/completions -H "Authorization: Bearer $env:RELAY_API_KEY" -H "content-type: application/json" -d "{\"model\":\"claude-opus-5-5\",\"messages\":[{\"role\":\"user\",\"content\":\"привет\"}]}"

Codex (~/.codex/config.toml):

    model = "gpt-6-sol"
    model_provider = "retool"
    model_reasoning_effort = "high"
    model_reasoning_summary = "detailed"
    web_search = "disabled"
    [model_providers.retool]
    name = "Retool relay"
    base_url = "http://127.0.0.1:8787/v1"
    wire_api = "responses"
    env_key = "RELAY_API_KEY"
    supports_websockets = false
    model_catalog_url = "http://127.0.0.1:8787/codex/models"

`/codex/models` предоставляет Codex-совместимые описания уровней мышления и
инструментов (`exec_command`, freeform `apply_patch`, namespaces субагентов).
Каждая запись несёт `supports_parallel_tool_calls: true`: релизы Codex до коммита
openai/codex 86b1123 (2026-08-14) объявляют поле обязательным, без него каталог не
разбирается, и клиент может слать `parallel_tool_calls: false`, которое relay
отклоняет вместе с tools; новые версии неизвестное поле игнорируют.
Встроенный server-side `web_search` Responses не реализован; клиентские
инструменты поиска, объявленные как function tools, проходят обычный bridge.

Claude Code: `ANTHROPIC_BASE_URL=http://127.0.0.1:8787` и
`ANTHROPIC_API_KEY=<тот же relay key>` (или `ANTHROPIC_AUTH_TOKEN`).
В bare-режиме Claude Code использует `ANTHROPIC_API_KEY`.

Для DeepSeek Harness используйте провайдера `retool` через OpenAI Chat:
`baseURL: http://127.0.0.1:8787/v1`, `thinkingFormat: deepseek`.
Схемы настроек трёх клиентов и границы IDE-команд — в
[docs/client-setup.md](docs/client-setup.md).

### Thinking и работа с проектом

Relay передаёт полученный от провайдера thinking отдельно от ответа:
Chat — `reasoning_content`, Responses — reasoning summary item/events,
Anthropic — thinking content blocks. Это только данные, которые Retool
раскрывает: скрытую цепочку рассуждений relay не восстанавливает и не выдумывает.
Если провайдер вернул пустой thinking, блок текста останется пустым.
В Claude Code блоки по умолчанию свёрнуты: `Ctrl+O` раскрывает их;
`showThinkingSummaries: true` включает отображение кратких сводок.

Opus 5.5 через Retool думает молча: приходит только начало блока и подпись.
Клиенты на OpenAI-совместимом API (OpenCode, Cline и другие на AI SDK) показывают
мышление лишь при непустом `reasoning_content`, поэтому в форматах Chat и Responses
relay в начале мышления отправляет метку `thinking_placeholder` (по умолчанию
«Модель думает…»). Метка служит только для отображения и в историю не попадает.
Пустая строка её отключает. В формате Anthropic открывается пустой блок thinking.

Уровень меняется настоящим полем Retool `modelProvider.reasoningEffort`:
`reasoning_effort` в Chat, `reasoning.effort` в Responses,
`thinking.type=adaptive` + `output_config.effort` в Anthropic.
Допустимые уровни конкретной модели перечислены в
`/v1/models → capabilities.reasoning_effort_levels`. Неподдерживаемый уровень
возвращает 400 до обращения к upstream. Явный `allow_effort_downgrade: true`
разрешает приближение известных уровней: берётся самый низкий уровень маршрута не ниже
запрошенного (`xhigh` у GPT-6.1 Sol и Terra — `max`), а если такого нет, верхний уровень
модели (`max` у GPT-5.5 — `high`); ниже запрошенного, пока есть уровень выше, relay не опускает.
Журнал хранит requested/effective effort
и причину выбора. Неизвестные `extra`/`ultra` отклоняются в обоих режимах.
Выключить рассуждение (`thinking: {type: disabled}` или effort `none`) умеют не все
модели: у Opus 5.5, Sonnet 5.5, GPT-5.5 и GPT-5 уровня `none` нет. Без настройки это 400,
и его текст называет `allow_effort_downgrade`; с настройкой берётся самый низкий уровень
маршрута (`low`, у GPT-5 `minimal`), а замена видна в журнале (`turn.begin`:
`requested_effort: none`, `effective_effort`, `effort_resolution: compatibility`) и в консоли.
Ещё одно исключение — сжатие истории клиентом: оно идёт на effort диалога, а не на
том, что прислал агент сжатия (`effort_resolution: cache_continuity`, см. «Ограничения»).
Модели с `none` (GPT-6 Sol, GPT-5.1, GPT-5.2) выполняют просьбу как есть в обоих режимах.
На 3 ноября Retool принимает для Opus 5.5 `high`/`max`, а сырой `xhigh` даёт 422.
GPT-6-sol и GPT-6.1-sol принимают `max`, но также отвергают `xhigh` с 422;
этот уровень не предлагается их каталогом Codex.
У моделей Claude `xhigh` ошибкой не бывает: Retool знает у них только low, medium, high и max, а Claude Desktop и другие
клиенты шлют один уровень всем моделям, поэтому relay отдаёт Retool вместо `xhigh` уровень `high` или `max`, как выбрано в
настройке `claude_xhigh_effort` (по умолчанию `high`, меняется в админке в группе «Модель и мышление» и применяется после
перезапуска: смена уровня посреди диалога сбрасывает подписанную ветку и кэш). От `allow_effort_downgrade` эта замена не
зависит; запрошенный `xhigh` остаётся в журнале (`requested_effort`, `effort_resolution: compatibility`). Остальные
недостающие уровни (`minimal`, `none`) по-прежнему требуют `allow_effort_downgrade`, а GPT и остальные маршруты без `xhigh`
отвергают его, как раньше. То же значение подставляется вместо `xhigh`, заданного уровнем по умолчанию
(`reasoning_effort`) или в профиле (`generation.effort`).
Legacy `thinking.budget_tokens` переводится в уровень;
точный бюджет токенов Retool этим интерфейсом не предоставляет.

Haiku 4.5 и оба GLM — исключение. Retool принимает для них `reasoningEffort` и ничего
не меняет: проба 2026-11-05 не нашла ни thinking, ни упорядочения по токенам и времени
([результаты](docs/reports/model-route-availability-2026-11-05.md#проба-effort-2026-11-05)).
У них `reasoning_effort_levels` пуст, а `reasoning_effort_control` равен
`accepted-ignored`: любое известное значение (`none`…`max`) и `thinking.budget_tokens`
принимаются без 400, в Retool не уходят, а имя параметра перечисляется в заголовке
`x-proxi-ignored-parameters` и в журнале. Это сделано, чтобы не ломать клиентов:
Claude Code шлёт для Haiku `thinking: {type: enabled, budget_tokens}`, остальные
копируют один уровень на все модели. Значение, которого не определяет ни один провайдер
(`extra`), по-прежнему даёт 400. У gpt-5-mini и gpt-5-nano уровни измеримо меняют
число токенов и время, они остаются выбираемыми.

Если клиент передал инструменты, модель получает его system/developer instructions,
историю и полные результаты инструментов. Файлы, изменения и тесты выполняются
инструментами клиента: workspace клиента имеет приоритет над папкой relay.
Поддержаны обычные function tools, Responses custom tools (`apply_patch`) и custom tools Chat
(`{"type": "custom", "custom": {…}}`: вызов возвращается как `type: "custom"` с одной строкой `input`).
Старые Chat `functions` и `function_call` relay отклоняет с 422: нужны `tools` и `tool_choice`.
Без инструментов клиента relay добавляет список файлов, Git-состояние и выдержки
AGENTS/README/PROTOCOL настроенного workspace; дополнительные чтения доступны
через локальный exec-протокол. Это не загрузка всего репозитория в prompt.

Исключение — запросы без инструментов от распознанных Claude Code/Desktop и
OpenCode. Основной чат этих клиентов всегда приходит со своими tools, а без них
они отправляют служебные вызовы: заголовки сессий, проверки Auto mode, сжатие
истории, пробы соединения. Такие запросы получают только system клиента: relay не
добавляет контекст проекта и инструкции relay, не выполняет `<exec_command>` из
ответа и не запускает orchestrator-повтор пустого хода (прямой транспорт для
`client-text` пустой ответ всё же повторяет до 2 раз; никогда не повторяются только
`auto-mode-check`, `session-title`, `connection-probe`). Это намеренное изменение:
запрос без инструментов от Claude Code, Desktop или OpenCode больше не может выполнять
команды через relay. Для curl и других клиентов без tools локальное исполнение работает
как раньше.

## Админка

`http://127.0.0.1:8787/admin/` — вход по тому же relay key (ключ передаётся только в заголовке).
Разделы: Сводка (баланс всех аккаунтов, попадание в кэш, TTFT, кредиты, графики),
Активность (вкладки «Ходы моделей» — трасса каждого хода с таймлайном, и «Все события» —
живой журнал с фильтрами, поиском, паузой, раскрытием JSON и экспортом в JSONL),
Аккаунты (пул: включение, приоритет, баланс, продление сессии, добавление и удаление),
Настройки (параметры relay, системная роль, адреса для IDE, каталог моделей),
Промпты (профили и правила системного промпта, предпросмотр, «что увидела модель»,
закрепления диалогов: [руководство](docs/prompt-control.md)).
Горячие клавиши — цифры по порядку разделов в боковой панели, светлая и тёмная темы.

Настройки пишутся в `config.json`; помеченные «сразу» действуют без перезапуска. Роль и режим
инструкций (`relay_system_prompt`, `relay_system_prompt_mode`) помечены «сразу»: они управляют
прежним путём, а профили и правила лежат в `prompts.json` и правятся в разделе «Промпты». Пока в
Настройках есть несохранённые правки, переход в другой раздел, «Выйти» и закрытие вкладки
сначала спрашивают подтверждение. Пока выбрана стандартная роль (`relay_system_prompt: null`),
показаны обе встроенные роли с пояснением, каким запросам какая достаётся: роль relay —
запросам без инструментов и без инструкций клиента, а также режимам `append`/`replace`;
отдельная роль — клиентам со своими инструментами, не приславшим инструкций. Собственная
роль заменяет обе. Она не длиннее 32 КиБ (UTF-8) и, если задан `max_prompt_bytes`, не больше
его половины: иначе каждый запрос получил бы 413, поэтому админка такую роль не сохраняет.
Пустая роль показывается как «Роль отключена». Текст роли в журнал не попадает: событие
`admin.settings` хранит только длину и короткий хэш. Так — начиная с этой версии: события
`admin.settings`, записанные раньше, могли сохранить текст роли (до 4000 символов), и они
остаются в `journal.jsonl` и `journal.jsonl.1`, пока их не вытеснит ротация; «Очистить» на
вкладке «Все события» очищает и эти файлы. Каталог моделей называет причину, по
которой у модели нет маршрута (нет ресурса у включённых аккаунтов, нужен BYOK или retention,
маршрут не поддерживается), а сводка показывает сессии включённых аккаунтов, а не первого в списке.

Журнал (`journal.py`) пишет события: HTTP-запросы, начало и конец хода, первый токен,
кредиты и кэш, вызовы инструментов, локальные команды, создание и вытеснение диалогов,
продление сессии Retool, прогрев кэша, действия в админке. Секреты маскируются.
В памяти хранится 20000 последних событий (около 40 минут при 500 событиях в минуту),
на диск они дописываются в `journal.jsonl`. Файл ротируется на `journal_max_file_bytes`
(50 МиБ) и хранит `journal_keep_files` прежних файлов (5: `journal.jsonl.1` — самый новый,
`journal.jsonl.5` — самый старый, он удаляется при следующей ротации). На диске лежит не
больше (`journal_keep_files` + 1) × `journal_max_file_bytes`, по умолчанию 300 МиБ — при
нагрузке четырёх агентов (около 0,8 МиБ в минуту) это шесть-семь часов; раньше было два
файла по 10 МиБ, то есть примерно полчаса, и улики теста терялись. После перезапуска
читаются последние 20 МиБ файлов, от нового к старому: буфер в памяти и метрики за сутки
не нуждаются в большем. Оба значения меняются в админке без перезапуска.

Метрики (`/admin/api/metrics`) считаются не по этому буферу, а по агрегатам с шагом
10 и 60 секунд за 24 часа 10 минут: окна 1, 6 и 24 часа не сокращаются из-за оборота
сырых событий. Поле `coverage` говорит, какую часть окна журнал реально покрывает
(`complete`, `covered_seconds`, `covered_from`, `oldest_event_ts`, размер сырого
буфера). После перезапуска агрегаты восстанавливаются из `journal.jsonl` и его прежних файлов
(последние 20 МиБ),
после очистки журнала покрытие начинается заново; окно длиннее покрытия помечено
как неполное, а не занижено молча. Агрегаты не переживают перезапуск сверх того,
что осталось в файлах журнала.

Событие, у которого известен аккаунт, несёт его тег в `data.account`: первые 8 символов
SHA-256 от `account_id` (или `page_uuid`); сам идентификатор в журнал не попадает. Тот же
тег стоит в `accounts[].account` ответа `GET /v1/balance`, поэтому по нему можно найти все
события одного аккаунта. Тег есть у `session.acquire`, `session.create`, `upstream.request`,
`upstream.attempt`, `upstream.usage` и остальных событий хода после получения сессии
(включая `turn.error` и `turn.end`, а также события транспорта и нативной истории вроде
`upstream.thinking_signal`, `upstream.rejected` и `native_history.*`), у `cache.keepwarm`,
`cache.keepwarm_usage` и `cache.keepwarm_stop`, у `auth.refresh`, `account.exhausted`,
`account.failover` и `admin.account`, а у HTTP-событий `http.request` и `http.error` — когда
запрос обслужил какой-то аккаунт. У `account.migrate` два тега: `from_account` (откуда
переехал диалог) и `to_account` (куда). `turn.begin` пишется до выбора аккаунта, поэтому
тега у него нет, как и у хода или запроса, которому не удалось получить сессию (например,
отказ 404/429/402/503 до начала ответа): аккаунт ещё не выбран. При повторе хода на другом
аккаунте тег каждой попытки свой, он не переходит на следующую.

`session.acquire` говорит и о нагрузке, с которой начался ход: `inflight_account` и
`inflight_total` — сколько ходов пул держал в работе на этом аккаунте и на всех, считая этот.
`wait_ms` у него считается от начала хода, ожидание слота `max_workers` в него не входит: его
пишет `slot_wait_ms` события `http.request`.

Для локальных Claude Code/Desktop и OpenCode журнал добавляет название приложения,
имя чата, ID сессии и агента. Имена читаются из локальных метаданных только этих
клиентов; `title_source` показывает источник названия (`claude-custom-title`,
`claude-summary`, `claude-desktop-session`, `opencode-session`, `client-header`).
Первое сообщение пользователя названием не используется никогда: без названия,
заданного самим клиентом, поле пусто. Для OpenCode 1.x можно скопировать
`scripts/integrations/proxi-session-labels.js` в `~/.config/opencode/plugins/`:
плагин передаёт актуальное название, включая переименования, и работает только для
провайдера с ID `retool-relay`. OpenCode 2.x читается из таблицы `session_v2` той же
локальной базы. Название чата и имя агента не меняют
affinity. ID вызывающей сессии (`x-proxi-session-id`, `x-opencode-session-id`,
`x-claude-code-session-id`) имеет приоритет над общим `x-session-affinity` родителя:
субагент получает отдельный диалог, историю, инструменты и прогрев кэша.
`x-claude-code-agent-id` также разделяет субагентов с общим ID сессии. Субагент Codex (порождённый, review, guardian) шлёт
`session-id` корня, свой `thread-id` и `x-codex-parent-thread-id`: с обоими заголовками он получает собственный диалог, а
родителем становится корень.
Связь с родителем берётся из `x-proxi-parent-session-id`,
`x-opencode-parent-session-id`, metadata или локальной базы OpenCode.
Пока идёт запрос субагента, родитель и его предки защищены от вытеснения,
а их keepwarm продолжает работать и после этого запроса, пока субагента ждут обратно: он ещё не дал окончательного
ответа (например, его ответ попросил долгий прогон тестов) и с его последнего запроса прошло не больше
`cache_keepwarm_subagent_idle` (см. «Prompt Caching»). Каждый запрос субагента начинает отсчёт простоя
родителя заново; после завершения действуют обычные лимиты простоя.
Названия чатов (заданные пользователем или клиентом) попадают в консоль, `relay.log`,
каждое событие `journal.jsonl` и метаданные диагностических снимков: учитывайте это,
когда передаёте эти файлы другим людям.

Запрос, которым клиент сжимает историю диалога, несёт `client_task: "compaction"` в каждом
своём событии (`turn.begin`, `upstream.usage`, `turn.end`, `http.request`, `native_history.*`,
`cache.*` хода), у Claude Code ещё `compaction_trigger` (`auto`, `manual`, `reactive`, из заголовка
`x-claude-code-compaction`). В консоли строка запроса заканчивается `TASK: compaction`, в админке у такого
хода стоит «сжатие». Это отдельная метка: `request_purpose` у такого запроса прежний.

Ответы содержат одинаковые `request-id` и `x-request-id`; ошибка также содержит
`request_id`. Отказы upstream 400/422 сохраняются в `<state-dir>/logs/upstream-400/`
(по умолчанию `logs/upstream-400/` рядом с relay; с `--state-dir` — внутри него;
либо `upstream_error_dir`) отдельными файлами: точное тело, текст ошибки и метаданные
с названием чата и ID запроса. В журнале и ответе есть `diagnostic_id`. Эти
локальные снимки содержат переписку; заголовки авторизации в них не записываются.
Одинаковые тела (по sha256) за время работы relay не дублируются. Число хранимых комплектов (body/error/metadata с общим штампом) ограничено
`upstream_error_max_dumps` (50, `0` — без ограничения): старые удаляются.

### Состояние диалогов после перезапуска

Раньше перезапуск relay стирал из памяти всё, что связывало диалог с кэшем Retool:
подписанные assistant/thinking-блоки, кэш-метки и аккаунт. Следующий ход длинного диалога уходил
с другим префиксом (без блоков thinking), а иногда и на другой аккаунт, и оплачивал запись
всего префикса заново: в живом журнале 30,40 кредита против 1,90 за обычный ход (записано
302 642 токена вместо 923). Теперь `conversation_state.py` хранит это на диске, и диалог после
перезапуска продолжается тем же телом запроса, на том же аккаунте. Кредиты это экономит, если диалог
вернулся, пока жив кэш Retool (5 минут от его последнего касания; остановленный relay кэш не греет):
в том же журнале первый перезапуск (пауза 2 мин 40 с) обошёлся бы в обычные 1,9 вместо 30,4. Если кэш
уже истёк, префикс запишется заново при любом хранении, но диалог остаётся на своём аккаунте и не
теряет подписанную историю. Файлы пишет только relay с этой функцией, поэтому при первом перезапуске
после обновления их ещё нет: экономия начинается со второго перезапуска.

- **Что хранится.** Для каждого диалога — один файл `<state-dir>/conversations/<хэш ключа>.state`:
  текстовый заголовок (версия формата, штамп блоков, ключ диалога, `account_id`, время записи, число веток
  и подписанных блоков) и сжатое состояние: две новейшие ветки native history (scope, клиентские
  сообщения для сверки, сообщения, отправленные upstream, с cache-метками, assistant-блоки с подписями),
  `_cached_turn_ends`, последний ключ кэша, размер префикса и время последнего касания кэша. Старые
  ветки (после правки истории, сжатия) в файл не попадают: они уже не продолжатся, а переписывались бы
  каждый ход (по замеру на живых по форме диалогах 8 веток — файл 8,3 МБ и 241 мс на запись, одна ветка —
  1,0 МБ и 35 мс). Только то, что relay сам получил от upstream; подписи, присланные клиентом, по-прежнему не
  доверяются. По живому журналу подпись thinking весит от 1 до 98 КБ (медиана 2,2 КБ, среднее 5,9 КБ), а
  файл длинного диалога — 1–2,3 МБ. Хранятся диалоги `session_mode: per_conversation` (и их текстовые
  сессии); ключ диалога длиннее 2048 символов (считаются символы самого ключа, а не его запись в JSON; это
  значение заголовка клиента) не сохраняется.
- **Что проверяется при чтении.** Заголовок несёт штамп блоков: он считается из описания форм блоков, которые
  relay записывает и возвращает upstream. Файл другой версии формата или с другим штампом (блоки собрал
  другой код) отбрасывается при запуске, не читаясь (причина `format`). Состояние с блоком неожиданного вида
  (неизвестный тип, `toolCallId` не строка, `toolInput` не объект, сообщение без роли) не применяется
  (`corrupt`): иначе оно ломало бы каждый запрос диалога до окончания срока хранения. Если ветка всё же
  ломает `resume`, она забывается вместе с записью в файле (`unusable`), а запрос идёт без подписей.
- **Когда пишется.** После каждого хода, изменившего диалог (записанная ветка, кэш-метки,
  ключ кэша), в фоновом потоке, не на пути запроса: временный файл `.write-*` в том же
  каталоге, `fsync`, атомарный `os.replace`. Поэтому жёсткая остановка (`taskkill /F`) посреди
  записи оставляет прежний целый файл, и теряется только ход, который шёл в момент остановки.
  При штатной остановке (Ctrl+C) очередь дописывается, а диалоги, чья запись не удалась,
  пробуются ещё раз. Сбой записи не влияет на запрос. Диск, отказавший в записи (`io_error`), даёт одно
  предупреждение и паузу в 30 с: relay не кодирует состояние и не повторяет то же предупреждение на каждом
  ходу (напоминание раз в 10 минут, пока диск не вернулся); остановка пробует писать независимо от паузы.
  Состояние, не вмещающееся в файл (`too_large`), не кодируется заново, пока диалог не станет легче.
- **Когда читается.** Лениво: когда запрос создаёт сессию диалога, у которого есть файл
  (после перезапуска и после вытеснения по простою `conversation_idle_timeout`). Сессия
  создаётся на том же аккаунте, если он включён, не исключён диспетчером (баланс, вход, часовой
  лимит) и имеет маршрут к модели, — те же условия, что у живого диалога; текстовая сессия простого
  чата возвращается на аккаунт собственного файла. Иначе действует обычный путь: диалог идёт на другой
  аккаунт без подписей, а файл остаётся (записью нового аккаунта после первого же успешного хода он
  заменяется). Подписи никогда не переносятся на другой аккаунт. Дальше `native_history.resume` работает
  как обычно: scope, эхо клиентских сообщений и результаты инструментов сверяются, несовпавшее
  отсекается. Файл читается в отдельном потоке (цикл событий не блокируется), один раз на диалог и не
  дольше 15 с: диск, который завис, стоит диалогу его состояния (`conversation_state.restore_failed`), но
  не запросу ответа. Сессия попадает в пул после того, как состояние в неё положено: запрос, отменённый
  во время чтения, не оставляет пустого диалога (чтение достанется следующему), а запрос того же диалога,
  пришедший в это время, ждёт сессию и продолжает с её ветками, а не начинает с нуля.
- **Сжатие после перезапуска.** Сжатие истории клиентом, пришедшее первым после перезапуска, видит ветки
  диалога: перед сверкой effort (см. «Сжатие истории клиентом» ниже) relay читает файл, и сессия потом использует это же
  чтение. Сжатие идёт на effort диалога (`cache.effort_kept`) и продолжает его подписанную историю, а не
  сбрасывает её (иначе запись префикса заново стоила около 28 кредитов).
- **Прогрев.** Восстановленный диалог не греется (keepwarm), пока не придёт настоящий запрос:
  сколько длился перезапуск, неизвестно, а пинг по остывшему кэшу платит полную запись.
- **Отказ upstream.** Если upstream ответил 400/422 на запрос, построенный из восстановленной ветки, и в
  тексте отказа названы thinking, подпись (`signature`), `redacted` или блоки (`blocks`, `tool_use`,
  `tool_result`), ветка забывается (и в файле тоже): следующая попытка идёт без подписей, а не повторяет
  отказ после каждого перезапуска. Отказ по другой причине (prompt не помещается в окно, поле хвоста
  запроса, общий «Invalid request format» без подробностей) ветку не трогает: отказ запроса сжатия не
  стоит диалогу его подписанной истории. Ветка, записанная живьём, остаётся, как и раньше.
- **Закрепления ревизий `prompts.json`.** Закрепление диалога за ревизией
  ([руководство](docs/prompt-control.md#закрепление-и-цена-смены-промпта)) тоже переживает перезапуск, пока включено
  `conversation_state`. Relay пишет его рядом с `*.state`, в подпапке `prompt-pins/`: `pins.json` (записи под
  ключами sha256, ключей диалогов там нет) и `revisions/<sha256>.json` (литеральные документы закреплённых
  ревизий). После перезапуска первый запрос диалога получает ту ревизию, на которой он начался: восстановленная
  ревизия получает новый номер и не становится текущей. Поэтому правка `prompts.json` между перезапусками не
  меняет head идущего диалога, и его подписанная ветка продолжается. Закрепление, не использованное 6 часов, и
  закрепление, чей документ ревизии потерян или испорчен, не восстанавливаются: диалог получает текущую
  ревизию, и если её head другой, подписанная ветка не продолжается (`native_history.reset` с `restored: true`
  показывает, что отброшена восстановленная ветка; причину называет `prompt.pin_dropped`). Подпапку сканер
  состояния не читает и не удаляет, а её файлы не входят в `conversation_state_max_total_bytes`: у закреплений
  свои пределы (4096 штук, 6 часов простоя). События: `prompt.pins_loaded`, `prompt.pins_saved`,
  `prompt.pins_error`, `prompt.pin_restored`, `prompt.pin_dropped`, `prompt.revision_restored`. Без каталога
  состояния закрепления живут только в памяти.
- **Пределы.** `conversation_state_max_conversations` (1000 файлов), `conversation_state_ttl`
  (86400 с от последней записи файла, не от последнего касания кэша), `conversation_state_max_file_bytes`
  (32 МиБ на файл в сжатом виде) и `conversation_state_max_total_bytes` (512 МиБ на каталог: считаются только
  файлы `.state`, временные `.write-*` в сумму не входят); всё — целые положительные числа (`true` и дробь
  при запуске отклоняются). Просроченное, лишнее и превышающее объём удаляется, самое старое первым;
  свежезаписанный файл не удаляется. Но когда файлов больше предела, первыми уходят крошечные состояния (не больше
  4096 байт: разовая задача или проверка, один запрос без истории), и только после них самые старые из остальных:
  иначе при потоке разовых запросов предел заполнен всегда, и состояние настоящей сессии уходит, едва становится
  самым старым (повтор 2316 записей a4, 2026-11-06: 133 из 280 диалогов с состоянием больше 4 КиБ теряли его через
  84–95 минут, медиана 87, а за сами записи было удалено только 266 состояний по 343 байта; при порядке «сначала
  мелкие» не теряет ни одно; первый запрос после перезапуска иначе записал бы весь префикс заново). Когда превышен
  объём, по-прежнему уходит самое старое: мелкие файлы его почти не уменьшают. Состояние, не вмещающееся в файл, теряет самые старые ветки; если не
  помещается и самая новая, оно не сохраняется (`save_failed`, `too_large`, один раз, пока диалог снова не
  сохранится), а устаревшая копия удаляется. Повреждённый файл, другая версия формата и файл другого
  диалога игнорируются и удаляются, но только файлы с именем и сигнатурой relay (`<32 hex>.state`, первая
  строка `PROXI-CONVERSATION-STATE`): всё остальное в каталоге relay не читает, не меняет и не удаляет,
  включая чужие `*.state`. Остатки прерванных записей (`.write-<хэш>-<8 hex>`) удаляются при запуске
  независимо от возраста, если их не держит открытыми другой процесс (так различает только Windows; два
  relay на одном каталоге не поддерживаются).
- **Приватность.** Файлы содержат переписку: тексты сообщений, результаты и аргументы
  инструментов, thinking (если upstream его присылает) и подписи. Они не шифруются и лежат только в
  state dir (рядом с журналом и трассами; без `--state-dir` — в `conversations/` рядом с relay,
  каталог в `.gitignore`). Подпапка `prompt-pins/` хранит литеральные документы закреплённых ревизий, то есть
  полные тексты ваших промптов, тоже открытым текстом. Если relay запущен из папки репозитория без
  `--state-dir` (и `conversation_state_dir` в `config.json` не задан), переписка и закрепления окажутся в
  `<репозиторий>/conversations/`, рядом с кодом. Чтобы держать их отдельно, запускайте
  `scripts\run_relay.ps1 -StateDir "$env:LOCALAPPDATA\Proxi\state"` (или `python proxy.py --state-dir …`).
  Права: на POSIX каталог и файлы создаются с `0700`/`0600`. На Windows: при
  Python ≥ 3.13 каталог доступен только владельцу, SYSTEM и Администраторам (файлы наследуют это), при
  3.11–3.12 права наследуются от родительской папки, то есть каталог читается всеми, кто видит эту папку.
  Передавайте каталог другим людям так же осторожно, как трассы. В журнал и консоль содержимое
  не попадает: только теги диалога и аккаунта, числа и причины. Сбросить всё: остановить relay и
  удалить каталог; выключить: `"conversation_state": false` (тогда ничего не пишется, не читается
  и каталог не создаётся).
- **Журнал.** `conversation_state.saved` (уровень debug: ветки, подписанные блоки, байты, время),
  `.save_failed` (`io_error` с паузой, `too_large`, `unserializable`, `capture`, `internal`), `.restored`
  (возраст файла и кэша), `.skipped` (состояние не применено, файл оставлен: `account_missing`,
  `account_disabled`, `account_unavailable`, `no_route`, `account_changed`), `.dropped` (`corrupt`,
  `format`, `key_mismatch`, `expired`, `limit_conversations`, `limit_bytes`, `too_large`, `emptied`,
  `rejected`, `unusable`), `.scan` (итог при запуске), `.disabled` (каталог недоступен), `.restore_failed` и
  `.load_failed`. Консоль печатает строку `[state] conversation restored` с тегом аккаунта и числами.
  Расчёт и ограничения: [docs/conversation-state-2026-11-06.md](docs/conversation-state-2026-11-06.md).

Лимит **5 фактических POST к модели** действует на один *шаг* клиентского запроса:
первая попытка и максимум четыре следующих. В него входят повторы пустого ответа,
повтор после обновления авторизации, fallback Assist и переключение аккаунта;
повтор не получает новый бюджет. Успешный локальный exec-шаг (команда выполнена)
начинает новый шаг (`AttemptBudget.new_step()`) со свежим счётчиком, поэтому цепочка
команд не обрывается из-за лимита. Число шагов ограничено только `max_exec_turns`:
при `0` шаги не ограничены, а при `max_exec_turns > 0` действует общий потолок
`5 × (max_exec_turns + 2)` POST на клиентский запрос. Исчерпание лимита даёт
`502 upstream_attempt_limit`; реальный предел (5 или общий потолок) указан в тексте
ошибки. Новый HTTP-запрос клиента получает новый бюджет. Фоновый keepwarm — отдельная
операция. После неудачных попыток внутри шага задержки составляют 0,5, 1, 2 и 4
секунды (первый POST шага не ждёт); отмена прерывает ожидание. Переход на другой
аккаунт (часовой лимит, баланс) не ждёт: отклонённая попытка бесплатна, а задержка
нужна, чтобы не бить повтором в тот же аккаунт; у нового аккаунта отсчёт задержек
начинается заново, лимит попыток общий. Служебные запросы
клиента (Auto mode, заголовки, пробы) пустой ответ не повторяют вообще.

Direct-повторы после пустого ответа передают то же тело: модель, effort, историю,
инструкции, инструменты и исходный `tool_choice`. Исключения: при Assist-fallback
(модель только в списке Assist) из тела убирается `metadata`, а `maxCompletionTokens`
в любом запросе не меньше 16. Relay не добавляет просьбы дать статус, не запрещает
инструменты и не меняет задачу ради получения непустого текста. Ответ с одним
thinking-блоком или подписью без текста/tool call отмечается как `thinking_only`.
Число одинаковых повторов задаёт `upstream_empty_retries` (по умолчанию `1`:
первый POST и один повтор, всего 2 одинаковых POST; `0` отключает повтор; в любом
случае не более 5 POST на шаг). Пока повтор ещё возможен, thinking и пробельный
текст попытки удерживаются и не передаются клиенту до первого полезного события
(непустой текст или tool call); события `credits`, `thinking_heartbeat` и `end`
проходят сразу. Служебные запросы и `upstream_empty_retries=0` стримятся без
удержания. Благодаря этому неудачная попытка не оставляет у клиента лишних
thinking-блоков и склеенных подписей: адаптер Anthropic закрывает открытый
thinking-блок на `usage_start`. Если все попытки пусты, клиент получает ошибку, а
не обещание будущей работы: `502 upstream_empty_turn`, текст которой называет возможную причину — отказ
классификатора провайдера. Так провайдер отказывает: HTTP 200 без текста и без причины остановки. Платные
пробы 2026-11-06 связали такие отказы с инструкциями в system клиента (блок persona-файла из `AGENTS.md`), а не с
формой запроса ([расследование](docs/reports/thinking-only-replies-2026-11-05.md)). Маркер `[RETRY]` существует только в agent-транспорте
(WebSocket); в direct он не используется.

Пустой ответ, на котором закончился лимит вывода клиента, пустым отказом не считается. GPT и GLM
соблюдают `max_tokens` / `max_completion_tokens` / `max_output_tokens` и пишут ровно столько токенов (60 из 60,
150 из 150, 300 из 300, 400 из 400 в пробах 2026-11-06), а модель с рассуждением при малом лимите тратит его на
рассуждение и ничего не пишет. Раньше relay повторял такой запрос с тем же лимитом, платил дважды и отвечал
`502 upstream_empty_turn`. Теперь ответ, закончившийся ровно на лимите (без целого вызова инструмента), не
повторяется и сообщается как обрезанный: Chat `finish_reason: "length"`, Messages `stop_reason: "max_tokens"`,
Responses `status: "incomplete"` с `incomplete_details.reason: "max_output_tokens"` (Codex при этом останавливается
сразу и печатает причину, без повторов: `ResponseIncomplete` у него не повторяется). Так же сообщается ответ, у
которого аргументы вызова инструмента на конце потока не стали JSON: вызов не объявляется целым (блок
`tool_use` не закрывается досрочно, `done` не ставится), хвост аргументов не «чинится» из сырого текста (клиент уже
получил свой, поэтому дельты всегда складываются в итог), цепочка не записывается как ветка продолжения и не становится
телом прогрева. Маршрут Claude лимит не соблюдает (на лимиты 16, 64 и 300 пришло 750–980 токенов), поэтому его ответ
обрезанным по лимиту не считается; эмуляция лимита для Claude — отдельная задача.

В direct-запросах с клиентскими инструментами непустой системный промпт
клиента передаётся без дополнительных указаний relay. При отсутствии такого
промпта остаётся стандартная роль помощника. Описания нативных инструментов
и параметров сохраняются целиком; лимит размера входящего запроса остаётся
применим ко всему запросу. Допустимые значения параметра тоже доходят до модели:
строковые `enum`, `const` и `anyOf` из таких значений — перечислением Retool, остальные
(числа, логические) — строкой `Allowed values: …` в описании поля. Без них модель угадывала
значение, и MCP-сервер клиента отклонял вызов (`Invalid option: expected one of …`).
Необязательное поле вида «X или null» (так их пишут Pydantic и многие MCP-серверы) сохраняет
тип X, а не превращается в строку. Инструмент строгий (`strict`) только по просьбе клиента: в
строгом режиме Retool делает обязательными все параметры, и модель заполняла необязательные
заглушками (`path: ""`, `items: []`, выдуманные `country` и `end_date` у tavily). В строгом
инструменте поле, допускающее null, остаётся «X или null» (Retool `anyOf` с веткой `null`) на любой
глубине: иначе модель выдумывала значения (`max_results: 10`, `since: "1970-01-01"`) или отказывалась
вызывать инструмент, а с веткой отвечает null (проверено живьём 2026-11-06 на gpt-5-mini и Haiku). Описание
инструментов входит в кэшированный префикс, поэтому после этого изменения первый ход каждого
открытого диалога один раз заново записывает кэш. Обновление инструкций меняет ключ кэша, поэтому
первый запрос с новым промптом может заново оплатить запись префикса. Так работает
прежний путь; с `prompts.json` head собирает выбранный профиль
([руководство](docs/prompt-control.md)).

Попытка с неуспешным исходом (`empty`, `thinking_only`, `error`, `truncated`) пишет
ограниченный `*-response.json` в `<state-dir>/logs/upstream-400/` (либо
`upstream_error_dir`); для успешных попыток (`content`) файл не создаётся, кроме
случая, когда на неё ссылается итоговая ошибка. Хранятся не более
`upstream_attempt_summaries_max` последних сводок (200, `0` — без ограничения).
Это сводка HTTP-статуса, разрешённых response headers,
типов событий NDJSON, неизвестных/неподдержанных форматов, счётчиков дельт,
stop/finish/refusal-сигналов и числового usage. Тексты генерации, аргументы tools,
thinking, cookies и заголовки авторизации в сводку не сохраняются. Поле
`request_body_sha256` позволяет сопоставлять тела без дублирования переписки.
Для пустого ответа приватный снимок тела запроса сохраняется не более одного на
пару «тип запроса + модель» за один запуск relay (отметка ставится только после
успешной записи); сводки ссылаются на него полем `request_diagnostic_id`.

Для временной подробной диагностики можно добавить оба поля в существующий
`config.json`, сохранив остальные настройки и авторизацию:

```json
{
  "client_trace_dir": ".agents/traces/client",
  "upstream_trace_dir": ".agents/traces/upstream"
}
```

Пути выше заданы относительно рабочего каталога, поэтому пример рассчитан на
запуск из корня проекта. После запуска relay в каждом каталоге создаются отдельные папки с ID запроса.
Каждая папка весит мегабайты, поэтому relay хранит в каждом каталоге только
`trace_max_folders` самых свежих папок трасс (200, `0` — без ограничения): без этого
трассы многоагентной сессии заняли десятки гигабайт за несколько часов. Чужие файлы
и папки с другими именами в каталоге трасс не удаляются. Трасса, в которую идущий запрос
ещё пишет, не удаляется, как бы она ни устарела относительно новых: если параллельных
запросов больше, чем `trace_max_folders`, папок временно больше предела, а лишние уходят
при очередной очистке после закрытия трасс (очистка идёт при создании каждой новой
трассы; со значением `0` она не выполняется вовсе).
Клиентская трасса сохраняет исходное тело запроса, разобранный запрос, события
relay и фактически записанное тело ответа. Upstream-трасса сохраняет тело каждой
попытки, полученные байты ответа и события парсера с временной шкалой и SHA-256.
HTTP-заголовки авторизации и cookies из заголовков не записываются. Однако
тела и события могут содержать полную переписку, вывод инструментов и любые
секреты, которые попали в сам текст; эти файлы не шифруются. Пути внутри
`.agents/` исключены из Git, но их права доступа и место на диске определяются
системой. Трассы не ротируются и могут быть большими. Отключите оба поля
значением `""` после расследования и самостоятельно удалите ненужные снимки.
Так же приватны сохранённые диалоги `<state-dir>/conversations/` (подписи, тексты, результаты
инструментов; см. «Состояние диалогов после перезапуска»), но они ограничены по числу, возрасту
и объёму и чистятся сами.
Регистрируются байты тела, полученные через HTTP-клиент, а не TLS-пакеты или
внутренний обмен Retool с поставщиком модели. При сбое записи трассы исходный
результат запроса сохраняется; для клиентской трассы пишется `client.trace_failed`.

Для явного платного повтора уже сохранённого upstream-тела, без запуска прокси:

```powershell
python scripts/replay_upstream.py --allow-paid --body "<state-dir>/logs/upstream-400/ИМЯ-body.json" --output ".agents/traces/НОВАЯ-ПАПКА"
```

Команда принимает только снимок с моделью `claude-opus-5-5`, делает не более
пяти запросов к модели и записывает в `manifest.json` флаг
`all_attempts_byte_identical` (сравнение сохранённых исходящих тел с исходным
файлом). Это повтор сохранённого тела Retool, а не восстановление отсутствовавшего
ранее сырого HTTP-запроса клиента. Первый запрос может повторно оплатить запись кэша.
Конфигурацию скрипт читает из временной копии: `account_id` не мигрируется в
`config.json`, lock-файлы не создаются, ротированные cookie не сохраняются. Чтобы
скрипт мог отправить до пяти одинаковых POST, он принудительно ставит
`upstream_empty_retries=4`. Подставьте путь к `<state-dir>`, имя снимка и новую, ещё
не существующую папку для результата.

После исчерпания попыток пустой ответ даёт `502 upstream_empty_turn`; ошибка
содержит `request_id`, `diagnostic_id` и `upstream_attempts`, а журнал —
`turn.error` и `turn.end: error`. Если клиент требовал инструмент
(`tool_choice=required` или конкретное имя), а модель его проигнорировала, ответ
тоже `502` с `diagnostic_id`/`upstream_attempts`: `upstream_empty_turn` — после
пустого ответа, `upstream_tool_choice_ignored` — после обычного текста или после вызова
только такого инструмента, которого клиент получить не может (сообщение называет его,
см. ниже). Ошибка записи
диагностического файла не заменяет исходную ошибку: в событии `upstream.attempt`
виден `diagnostic_saved=false`. Обрыв соединения с Retool, включая `ssl.SSLError`/
`OSError` во время стрима, возвращается как 502 `upstream_error`, таймаут — как 504
с теми же полями диагностики. После начала SSE HTTP-заголовок уже равен 200:
ошибка передаётся SSE-событием `error`, без успешного `finish_reason`.

Вызов инструмента, которого клиент получить не может (необъявленный; при выборе по имени —
любой другой, чем названный), relay не передаёт и записывает как `tool.call_dropped`. Раньше
такой вызов оставался в ветке подписанной истории: клиент его не повторял, следующий запрос не
продолжал ветку (`native_history.reset`, префикс писался заново), а ответ, в котором был только
он, считался ответом (a5, C4). Теперь на маршруте Anthropic ветка — это ответ без таких вызовов:
блоки thinking с подписями остаются теми, что пришли, а сообщение ветки совпадает с тем, что
получил клиент (событие `native_history.pruned`; `kept: false`, если ничего не осталось, и тогда
ветка не пишется, а ответ не становится телом прогрева). На других маршрутах ветка пишется как
прежде: OpenAI требует, чтобы за блоком рассуждения шёл элемент, с которым он был создан. Что
Anthropic принимает историю без вызова после подписанного thinking, на живом маршруте ещё не
проверено: после перезапуска следующий запрос за `native_history.pruned` должен дать
`native_history.resume`, а не 400.

Запуск проверенного checkout с существующими учётными данными и отдельными логами:
`python proxy.py --config <repo>\config.json --state-dir "$env:LOCALAPPDATA\Proxi\state"` (PowerShell).
`--config` использует `relay_key.txt` рядом с выбранным конфигом.
Те же параметры поддерживает `scripts/run_relay.ps1` (`-Config`, `-StateDir`).

Настройки реальных клиентов и дочерних агентов можно проверить без запросов к
провайдеру: `python scripts/probe_client_settings.py claude`, аналогично
`opencode` и `opencode2`. Проверка поднимает локальный имитатор API и проверяет
`high` у родителя и дочернего агента. Адрес имитатора подменяется только у провайдера
`retool-relay`, поэтому запуск OpenCode закреплён за ним: проверка передаёт `--model`, а
модель по умолчанию, малую модель и модели агентов, стоящие на другом провайдере, заменяет
моделью `retool-relay` (ваши модели `retool-relay` остаются и проверяются). Если разрешённая
конфигурация клиента всё же называет модель другого провайдера, проверка отказывается до
первого запроса к модели. Она создаёт тестовые сессии OpenCode;
внешние инструменты модель не вызывает. При необходимости укажите `--executable`.
Проверка OpenCode также сверяет каталог и определения вариантов: Desktop 2.2.5
при преобразовании старой схемы игнорирует blacklist и не применяет
`variants.xhigh.disabled`. Удаляйте неподдерживаемые варианты и модели из самих
`provider.<name>.models`; для настроенной пары CLI1/Desktop2 отсутствие xhigh
проверено в обоих фактических каталогах.

Разбор задержек: `python scripts\turn_breakdown.py journal.jsonl --last 20` раскладывает каждый
ход на обработку контекста (до начала мышления), скрытое мышление, генерацию аргументов
инструментов и текст. Аргументы инструментов стримятся клиенту по мере генерации.

Сборка фронтенда: `cd web; npm ci; npm run build` (результат в `web/dist`). Сборка закоммичена,
и CI падает, если свежая пересборка отличается от неё: после правок в `web/src` пересоберите
и закоммитьте `web/dist`.
Проверки админки (синтетические данные, relay не нужен): `node --test web/tests/turns.test.mjs`;
браузерные сценарии `cd web; npx playwright test` (нужен Chromium: `npx playwright install chromium`
или путь к установленному в `PW_CHROMIUM`); дизайн-гейт с axe и проверкой переполнения
`cd web; npm run test:design`.

Консоль: cache `read` выделен бирюзовым, `write` — янтарным. Запись от 50 000
токенов получает красную метку `WRITE HIGH`; рост write относительно предыдущего
запроса того же диалога/модели минимум в 4 раза и на 8192 токена — `WRITE SPIKE`.
Большой объём чтения из кэша сам по себе не вызывает предупреждения.
Метки остаются видимыми и без цвета. Это подсветка телеметрии, не изменение кэширования.

После каждого модельного HTTP-запроса консоль печатает `balance` аккаунта, который
обслужил запрос (при нескольких аккаунтах — с `account=<tag>`), месячный `limit` и
`spent` за запрос, включая повторные upstream-попытки. Остаток берётся из уже
полученного баланса этого аккаунта с учётом локальных списаний. Метки: `UNAVAILABLE` —
нет данных; `UNREPORTED USAGE` — upstream не сообщил стоимость; `STALE` — снимок
старше 30 с или последнее обновление не удалось; `LOCAL ESTIMATE` — снимок моложе 30 с
с вычтенными локальными списаниями; `CACHED` — снимок моложе 30 с без списаний после
замера. Баланс запрашивается раз в 300 с, поэтому обычно видно `STALE` (это возраст
данных, не обязательно ошибка). Ради этой строки сетевой запрос не выполняется и
ответ модели не задерживается. Подробнее — [docs/reports/console-logs-2026-11-03.md](docs/reports/console-logs-2026-11-03.md).

`python scripts/watch_relay.py` показывает цветной хвост фонового `relay.log`
из `%LOCALAPPDATA%/Proxi/state/` (или укажите путь первым аргументом).
`--demo` показывает синтетические read/write/balance-примеры без обращения к модели,
`--no-follow` печатает только последние строки. В терминале цвет включается
автоматически; `NO_COLOR` отключает, `FORCE_COLOR=1` принудительно включает его.
Супервизор (`scripts/run_relay.ps1`) пишет `relay.log` явно в UTF-8 без BOM и без
ANSI-кодов; просмотрщик раскрашивает файл при чтении. Старые логи, записанные
Windows PowerShell 5.1 через `*>>`, могут быть в UTF-16 или смешанными: `watch_relay`
вырезает из них NUL, но кириллица в таких файлах может быть повреждена.

## Конфигурация

Все ключи с дефолтами — в config.example.json. Важное:

| ключ | смысл |
| --- | --- |
| min_account_balance | 20 — резерв failover: аккаунт ниже порога выбирается последним, но обслуживает, пока баланс > 0 (в том числе единственный аккаунт) |
| account_balance_interval | 300 — период проверки баланса каждого аккаунта, с; `0` — раз в час |
| account_refresh_parallel | 3 — сколько фоновых проверок аккаунтов (продление/баланс) диспетчер ведёт одновременно; на запрос баланса по `/v1/balance`, `/health` и в админке не влияет (там до 8 параллельно) |
| account_move_keeps_history | false — диалог, которому приходится сменить аккаунт (баланс, вход, часовой лимит, нет маршрута), оставляет на старом подписанные блоки рассуждений: его первый запрос на новом отличается от закэшированного, и весь префикс пишется заново (79 тыс.–580 тыс. токенов в журнале, 8–58 кредитов, 38 с до первого токена). Кэш провайдера при этом общий для аккаунтов (префикс, записанный на одном аккаунте, целиком прочитан на другом: 12 пар из 12, 2026-11-07), так что переписывать его заставляет потеря подписей, а не смена аккаунта. `true` — подписанные ветки едут с диалогом как восстановленные с диска (`carried_branches` в `account.migrate`); принимает ли upstream подпись на другом аккаунте, не проверено, поэтому отказ, который называет блоки, забывает ветки, а следующий запрос уходит без подписей, как раньше. Применяется сразу |
| account_rate_limit_cooldown | 900 — на сколько секунд аккаунт уходит из пула после ответа Retool о часовом лимите managed-ключей (1–3600); повтор сразу после возврата удлиняет паузу на 5 минут за раз, потолок — большее из этого значения и 20 минут; заголовок `Retry-After`, если Retool его пришлёт, главнее. Применяется после перезапуска |
| account_rate_limit_wait | 0 — сколько секунд (0–120) запрос диалога с префиксом не меньше 8000 токенов один раз ждёт аккаунт, ответивший о часовом лимите, и спрашивает его ещё раз, прежде чем диалог переедет на другой аккаунт и запишет весь префикс заново; аккаунт на время ожидания не исключается; `Retry-After`, если Retool его пришлёт и он не больше значения, задаёт ожидание, без него ждём всё значение; `0` — переезжать сразу. Применяется сразу. Подробности: «Установка», пункт про часовой лимит Retool |
| upstream_error_max_dumps | 50 — сколько наборов отклонённых 400/422 хранить в `logs/upstream-400`; `0` — без ограничения, отрицательное значение relay не принимает при запуске. Ключ необязательный: если его нет, действует 50 |
| session_mode | per_conversation (по умолчанию), per_request (новый тред на каждый запрос) или shared (один тред) |

### Как читается политика команд

Команда режется на сегменты по переводам строк и разделителям `&& || | ; &` **вне кавычек**.
Для каждого сегмента проверяется первое слово. Для `powershell`, `pwsh` и `cmd` тело после
`-Command` / `-c` / `/c` проверяется рекурсивно по списку разрешённых cmdlet-ов
(`Get-Content`, `Get-ChildItem`, `Select-String`, `dir`, `type`, `findstr`, `ping` и т. п.).
Поэтому `powershell -Command "Get-ChildItem; Get-Date"` проходит, а `powershell -c "calc"` — нет.
`git` под allowlist выполняет только команды чтения (`status`, `log`, `diff`, `show`, `blame`, `grep`, `ls-files`,
`branch`/`tag` для списка и т. п.), а также `fetch` и `push` к настроенным remote, без `--exec`. Остальные подкоманды
(`rebase`, `clone`, `ls-remote`, `archive`, `commit`, `reset`, `checkout`, `clean`…) требуют `allow_all`: среди них
были формы, которые запускали любую программу (`rebase -x`, `clone -u`, `ls-remote --exec`). В теле PowerShell запрещены
`$` в любом месте, `ForEach-Object` (он вызывает методы, например `InvokeScript`) и провайдеры `variable:`, `env:`,
`function:`, реестра: свойства читает `Select-Object -ExpandProperty`.
`allowlist` ограничивает **список программ**, а не файловую систему: `type C:\Windows\win.ini`
или чтение другого абсолютного пути возможны. Allowlist не является песочницей
файловой системы. Подстановки cmd, PowerShell script blocks/вложенные выражения,
неявные и encoded shell-команды блокируются; Python/Node/npm/curl не разрешены
по умолчанию. Полноценные правки и тесты используйте через инструменты клиента
с его разрешениями. `allow_all` остаётся явным выбором владельца relay.

Таймауты: ход — 900 с (`turn_timeout`), чтение кадра — 120 с (`recv_timeout`), команда — 300 с.
Таймаут чтения кадра сам по себе не завершает генерацию. Эти значения ограничивают
максимальное ожидание; успешный ответ отправляется сразу после готовности.
Количество шагов исполнения не ограничено (`max_exec_turns: 0`): лимит 5 POST действует
на каждый шаг отдельно, а не на всю цепочку команд. Ограничение шагов можно
включить вручную: тогда на исчерпании агент получает финальный ход без команд, а общий
потолок POST на клиентский запрос равен `5 × (max_exec_turns + 2)` (ошибка
`502 upstream_attempt_limit`). Отдельно
стоит предохранитель от цикла: если одна и та же команда повторяется, исполнение
останавливается и агент обязан дать сводку.
`max_tokens` валидируется по модели. Контексты, output caps, рекомендуемые уровни
и границы подтверждения сведены в [аудите каталога](docs/reports/model-catalog-audit.md).

### Системный промпт: `prompts.json`, инструкции клиента и роль relay

Что модель увидит в system, решает файл `prompts.json`. Если его нет, остаются прежние
настройки роли.

**`prompts.json`.** Файл лежит рядом с `config.json` (другой путь — ключ `prompts_file`) и внесён
в `.gitignore`; образец — [prompts.example.json](prompts.example.json). Он задаёт профили (шаблон
system с переменными, правки system клиента, истории и описаний tools) и правила, которые выбирают
профиль по клиенту, модели, назначению запроса или заголовку `x-proxi-profile`; профиль можно
выбрать и именем модели `<модель>@<профиль>`. Например, свои правила перед system OpenCode:

```json
{
  "version": 1,
  "texts": {"my_rules": "Отвечай по-русски. Не меняй файлы без явной просьбы."},
  "profiles": {"rules-first": {"head": "{{text:my_rules}}\n\n{{client_system}}"}},
  "rules": [{"name": "opencode", "if": {"client": "opencode", "tools": true}, "use": "rules-first"}]
}
```

- Без файла, а также для запросов, которые не поймало ни одно правило (при незаданном
  `default_profile`), поведение прежнее побайтно. Исключение — служебные запросы: их забирают защитные
  правила и отдают профилю `passthrough` (system клиента без изменений). При `standalone` это то же самое,
  при `append`/`replace` служебные запросы OpenCode (title, summary, compaction 1.x) роли прежнего пути больше
  не получают.
- Файл применяется без перезапуска (его читают и каталоги `/v1/models` и `/codex/models`). Невалидный файл
  не ломает работу: остаётся прежняя ревизия, пишется событие `prompt.config_error` (в журнале краткое описание
  без цитат, полный текст в админке), в админке виден баннер. Удаление файла подтверждается двумя проверками
  с интервалом в секунду, так что редактор, сохраняющий «удалить и создать», диалоги на прежний путь не уводит.
- Активные диалоги закреплены за своей ревизией: смена профиля действует на новые диалоги, и после
  перезапуска тоже, если включено сохранение состояния диалогов (закрепления лежат в
  `<state-dir>/conversations/prompt-pins/`, см. «Состояние диалогов после перезапуска»). «Применить ко всем» в
  админке сбрасывает кэш каждого активного диалога один раз (порядок величины — 10–44 кредита на большой
  диалог Opus 5.5, у Sonnet 5.5 вдвое меньше).
- Служебные запросы (заголовки диалогов, классификатор Auto mode, проба соединения, сжатие OpenCode 1.x и
  Claude Code с заголовком класса) идут со своими промптами клиента: их защищают встроенные правила. Сжатие
  OpenCode 2.x защитой не узнаётся намеренно: оно приходит с system и tools чата и идёт по профилю чата, так
  что кэш сохраняется. Правила с `override_protected` судятся раньше защитных.
- Тексты `{"file": ...}` читаются только из папки `prompts/` рядом с файлом (`.md` и `.txt`). Регулярные
  выражения исполняет модуль `regex` с таймаутом на операцию и бюджетом на вызов; правка, упёршаяся в таймаут,
  не применяется. Head не больше 1 МиБ (иначе 413 `prompt_too_large`), рост текстов правками ограничен. Роли
  профиля (`{{role}}`, `{{native_role}}`) берутся из `relay_texts` или встроенные: `relay_system_prompt` из
  Настроек действует только на прежний путь. Все пределы — в разделе «Пределы движка» руководства.
- В журнал попадают только длины и sha8; полный текст виден в админке («Предпросмотр» и
  «Что увидела модель»), а в закреплениях на диске (`prompt-pins/`) лежат документы ревизий открытым текстом.

Руководство с рецептами (заменить промпт OpenCode, вырезать разделы и `<env>`, убрать
напоминания, профиль по заголовку для Claude Code, Codex, Desktop и OpenCode, виртуальные
модели, тексты Codex) — [docs/prompt-control.md](docs/prompt-control.md).

**Прежний путь.** `relay_system_prompt` и `relay_system_prompt_mode` работают как раньше, пока
нет файла, правило не поймало запрос или выбрало `$legacy` (только там: head, который собрал профиль,
их не читает); изменения через админку действуют
без перезапуска. Изменения поведения, которые стоит знать до обновления:

- **Клиентский system забирает запрос у relay.** Любой непустой `system` /
  `instructions`, включая неизвестную IDE без tools, делает запрос клиентским: relay
  не добавляет project context и `[LOCAL EXECUTION]` и не исполняет `<exec_command>`
  из ответа модели. Режимы `relay_system_prompt_mode` (`append`, `replace`) возвращают
  только текст политики, но не контекст проекта и не исполнение. Это затрагивает
  скрипты и ботов, которые ходили через relay со своим `system` и рассчитывали, что
  relay сам исполнит команду. Чтобы получить роль relay вместе с контекстом и
  исполнением (по `project_context` и `exec_policy`), отправляйте запрос без `system` /
  `instructions` и без tools; пустой system и system из одних пробелов считаются
  отсутствующими.
- **Поздние system/developer-сообщения остаются на месте как user-текст.** В head
  попадают только ведущие system/developer и top-level `system` / `instructions`.
  Остальные с непустым текстом остаются там, где их прислал клиент, user-сообщением
  в обёртке `<system-reminder>`, и не меняют head, ключ кэша и подписи рассуждений.
  Пустые записи (например, `output_config.effort` с `content: []`) ничего не
  добавляют, effort берётся из последней. Ответ несёт `x-proxi-system-messages:
  inline-as-user-text`, приоритет оператора не сохраняется. Inline-блоки
  `tool_addition` и `tool_removal` (поздние объявления и отзыв tools у Claude Code)
  не применяются и не попадают в текст: они названы в `x-proxi-ignored-parameters`
  и в журнале, запрос не отклоняется. С `prompts.json` обработку таких записей выбирает
  профиль: `history.mid_system` (`keep`, `wrap`, `plain`, `drop`).
- **Напоминание на один запрос и отмена хода не сбрасывают подписанную историю.** Цель
  OpenCode шлёт `<system-reminder>` с каждым запросом и не хранит его: следующий запрос без
  напоминания продолжает подписанный ответ, а напоминание остаётся там, где его видела модель
  (`native_history.resume`: `reminders_kept`). Отмена хода (`/undo` и Revert в OpenCode,
  `/rewind` и двойной Esc в Claude Code, двойной Esc в Codex, правка и повтор в Claude Desktop)
  продолжает финальный ответ хода перед отменённым: relay держит три последних таких ответа,
  и провайдер читает разговор до этой точки из кэша, пока кэш жив (`rewound: true`).
- **Только пробелы в `relay_system_prompt`** означают «без роли», как `""`.

Подробности, живые проверки и границы доказательств описаны в
[системной политике](docs/relay-quality-and-prompts.md).

## Каталог моделей

В `models.CATALOG` сохранены 40 записей с метаданными. На проверенном пуле
публикуются 27 канонических моделей, каждая ответила на синтетические вопросы;
`/health.models` отдаёт это число, а не размер реестра. Среди них GPT-6.1 Terra,
GPT-4.1 и работающий Haiku 4.5 через Assist. Временная ошибка или пустой ответ не
считаются доказательством отсутствия модели. `route_checked_at` стоит только у
маршрутов, которые действительно проверялись живым запросом: у шести Gemini проб
не было, и даты у них нет.

Публичный каталог учитывает ресурсы включённых аккаунтов, несовместимые endpoints
и условия BYOK/retention. Fable требует доступной организации настройки retention
или подходящего BYOK; Astra и Google требуют собственных ресурсов провайдера.
Статус метаданных отдельно от доступности. Причины и точные Model ID приведены в
[актуальной матрице маршрутов](docs/reports/model-route-availability-2026-11-05.md).
Каталог считается так же, как маршрутизация: ресурсы корня наследуются аккаунтом
того же tenant (как в `SessionPool`), а в режиме `session_mode: shared` без области
контекста запросы обслуживает только первый аккаунт, поэтому учитывается только он.

Anthropic сняла Opus 4 (2026-06-15), Opus 4.1 (2026-08-05) и Sonnet 4 (2026-06-15):
запросы к ним завершаются ошибкой, и собственный ключ их не возвращает. Они остаются в
реестре как `unsupported` с датой снятия и не публикуются даже с BYOK-дескриптором.
Sonnet 4.5 помечен Anthropic как deprecated (2026-09-30) и отключается 2026-11-30:
до этого дня он публикуется, начиная с 2026-11-30 (UTC) relay скрывает его сам, без
перезапуска, и отвечает на запросы 404 с датой.

Если все аккаунты выключены, `/v1/models` и `/codex/models` возвращают пустые
списки. Так задумано: каталог описывает то, что можно вызвать сейчас, а при нуле
включённых аккаунтов вызвать нечего (запросы получают 503 `no enabled account`).
Такое состояние возможно только после правки `config.json` (админка не даёт выключить
последний включённый аккаунт); включите любой аккаунт в админке, и список вернётся
сразу, без перезапуска.

Модель по умолчанию (`model` в конфиге) публикуется по общим правилам, исключения для
неё нет. Если она скрыта (нужен BYOK, нет ресурса, снята, нет включённых аккаунтов),
запросы без поля `model` получают ошибку, поэтому при старте relay пишет
`WARNING: default model '…' is not published (причина)` в баннер и событие журнала
`relay.warning`; туда же попадают предупреждения конфигурации (например, `provider_access`
в корне при наличии `accounts[]`). В админке это предупреждение пока не выводится:
для него нужен вывод в `web/src`, а данные дают `models.default_model_warning`.

Провайдер и ресурс определяются записью модели в каталоге и конкретным аккаунтом:
Anthropic, OpenAI, Google или Retool-fast. Секреты и ресурсы между аккаунтами не переносятся.

### Окно контекста у клиентов Claude

Для Claude `/v1/models` отдаёт `max_input_tokens` только там, где известен предел
маршрута (872 000 для Opus 4.6, 4.7, 4.8, 5, 5.5 и Fable 5; 936 000 для Sonnet 4.6), и
никогда не отдаёт `supports_1m`: Claude Desktop читает и то и другое от 1M как «окно
подтверждено для вашего развёртывания» и добавляет отдельный пункт «1M context window».
Окно модели остаётся в `context_window`. Семейства Desktop (`anthropic_family_tier`) —
`opus`, `sonnet`, `haiku`, `fable`, `mythos`.

Claude Code за `ANTHROPIC_BASE_URL` считает у Opus 4.7 и новее, Sonnet 5 и новее и у Fable
нативное окно 1M и не видит меньший предел сервера, а маршрут Retool принимает на вход 872 000.
Задайте `CLAUDE_CODE_AUTO_COMPACT_WINDOW` ниже меньшего из пределов, которыми вы пользуетесь,
например `CLAUDE_CODE_AUTO_COMPACT_WINDOW=800000` (допустимо от 100000 до 1000000; суффиксы
`200k`/`1M` с версии 2.1.304; значение общее для всех моделей сессии и ограничено окном
модели). Без него Claude Code сжимает контекст нативных 1M-моделей примерно на 967K токенов,
выше резерва маршрута. Источники и подробности: [аудит каталога](docs/reports/model-catalog-audit.md).

## Коды ответов

400 битый JSON/заголовки, а также отказ upstream 400/422 (возвращается как локальный
400 `invalid_request_error`, не 502), 401 нет или неверный relay-ключ, 402
`insufficient_credits` (кредиты закончились на всех подходящих аккаунтах), 404 неизвестный маршрут или
модель, 405 неверный метод, 413 слишком большое тело, 415 не JSON, 422 неверные типы
полей, 429 локальный rate limit или лимит Retool (`rate_limit_error`; с `Retry-After`,
когда все аккаунты упёрлись в часовой лимит Retool; значение — целые секунды, всегда с
округлением вверх, как требует RFC 9110), 502 отказ
upstream/сессии, 503 upstream недоступен или нет аккаунта с маршрутом к модели,
504 таймаут хода.

404 возвращается и для модели, которую ни один аккаунт не может обслужить по настройке
(`not_found_error` с причиной: снята провайдером, неподдерживаемый маршрут, нужен BYOK
или retention, нет ресурса провайдера; повторять бессмысленно). 503 «нет аккаунта с
маршрутом» значит другое: пригодный аккаунт есть, но сейчас выключен или требует нового
входа; повтор возможен.

Коды 502 с диагностикой (`diagnostic_id`, `upstream_attempts`):

| код | когда |
| --- | --- |
| `upstream_empty_turn` | все попытки вернули пустой или thinking-only ответ; либо клиент требовал инструмент, а модель ответила пусто |
| `upstream_tool_choice_ignored` | клиент требовал инструмент (`required`/имя), а модель ответила обычным текстом или вызвала только то, что клиент получить не может (сообщение называет эти вызовы) |
| `upstream_attempt_limit` | исчерпан лимит 5 POST на шаг либо общий потолок `5 × (max_exec_turns + 2)`; реальный предел указан в сообщении |
| `upstream_auth_error` | Retool отверг сессию (401/403) после попытки refresh |
| `upstream_error` | прочий отказ upstream, обрыв соединения (включая `ssl.SSLError`/`OSError` при стриме) |

Таймаут upstream возвращается как 504.

В диалекте Messages (JSON и SSE `event: error`) `error.type` всегда один из документированных
типов Anthropic ([список](https://platform.claude.com/docs/en/api/errors)): собственный код
relay переводится, и клиент не встречает тип, которого его обработчик ошибок не знает.
Собственный код остаётся в `ApiError.code`, в журнале (`http.error`), в диалектах OpenAI и в
самом ответе Messages: поле `error.relay_code` есть везде, где тип заменил код
(`upstream_error` → `api_error`, `insufficient_credits` → `billing_error`), и отсутствует,
когда они совпали (`rate_limit_error`).

| код relay | тип Messages |
| --- | --- |
| `invalid_request_error`, `unprocessable_entity`, `unsupported_media_type`, `method_not_allowed`, `context_length_exceeded` | `invalid_request_error` |
| `unauthorized` | `authentication_error` |
| `insufficient_credits` | `billing_error` |
| `forbidden` | `permission_error` |
| `not_found_error` | `not_found_error` |
| `conflict` | `conflict_error` |
| `payload_too_large`, `prompt_too_large` | `request_too_large` |
| `rate_limit_error` | `rate_limit_error` |
| `service_unavailable` | `overloaded_error` |
| `upstream_timeout` | `timeout_error` |
| `upstream_error`, `upstream_auth_error`, `upstream_invalid_output`, `upstream_empty_turn`, `upstream_attempt_limit`, `upstream_tool_choice_ignored`, `internal_error` | `api_error` |

Код, которого нет в таблице, переводится по статусу: 401 `authentication_error`, 402
`billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413
`request_too_large`, 429 `rate_limit_error`, 503 `overloaded_error`, 504 `timeout_error`, прочие
5xx `api_error`, прочие 4xx `invalid_request_error`.

### Вызовы инструментов в потоке Responses

Вызов закрывается событиями `response.function_call_arguments.done` (у custom-инструмента
`response.custom_tool_call_input.done`) и `response.output_item.done` в тот момент, когда upstream
дописал его аргументы, а не когда закончился весь ответ. Codex запускает инструмент по
`response.output_item.done` его элемента и кладёт элементы в историю в порядке этих событий, поэтому
раньше первый вызов пачки ждал, пока будут написаны остальные: 0,45–2,8 с для пяти–восьми коротких
вызовов, 11–21 с, когда каждый вызов писал скрипт (Opus, пять таких вызовов: 20,9 с; замеры a4 от
2026-11-06). Проверено настоящим Codex 0.167.0 на своём тестовом сервере Responses (два вызова, второй
пишется на 6 с позже): при событиях в конце ответа первый инструмент запустился на 9,0 с, пачка закончилась
на 10,5 с; при раннем `done` первый запустился на 2,8 и 4,5 с (два прогона), пачка закончилась на 6,9 с.
Перед вызовом закрываются все прежние элементы (рассуждение, сообщение), чтобы история сохранила порядок
вывода; незаконченный вызов не пропускает вперёд вызовы после себя (иначе закрылся бы и он, с половиной
аргументов). Текст и рассуждение, пришедшие после закрытого элемента, открывают новый элемент. После
таймаута завершённый вызов остаётся `completed`, `incomplete` только то, что оборвано. Тот же приём у
Messages (блок `tool_use` закрывается по окончании вызова); у Chat Completions события окончания
отдельного вызова нет.

### Ошибка после начала потока Responses

Если запрос Responses упал, когда поток уже открыт (невалидный structured-ответ, обрыв
upstream, таймаут хода, отказ по кредитам или лимиту), relay присылает `event: error`, затем
терминальное `response.failed` и `data: [DONE]`. У `response.failed` тот же `id`, что у
`response.created`, `status: "failed"` и `error: {code, message}`; у обоих событий есть
`sequence_number`, а у `error` ещё `relay_code` (собственный код relay), `request_id` и,
если есть, `diagnostic_id`. Форматы ошибок потока Chat и Messages не менялись.

Код (`error.code`) решает, повторит ли клиент запрос. Codex 0.164.0 игнорирует `error` и без
`response.failed` видел обрыв до `response.completed`, молча повторял запрос до
`stream_max_retries` (5) раз, а повторы оплачиваются. Теперь он классифицирует код
(`codex-api/src/sse/responses_error.rs`, `protocol/src/error.rs`, `core/src/responses_retry.rs`):

| код relay | код Responses | Codex |
| --- | --- | --- |
| `upstream_invalid_output`, `upstream_empty_turn`, `upstream_attempt_limit`, `upstream_tool_choice_ignored`, `invalid_request_error`, `unprocessable_entity`, `prompt_too_large` и прочие 4xx | `invalid_prompt` | не повторяет, печатает сообщение |
| `insufficient_credits` | `insufficient_quota` | не повторяет, печатает свой текст «Quota exceeded…» |
| `context_length_exceeded` (провайдер ответил, что вход больше окна контекста модели: «exceeds the context window», «prompt is too long») | `context_length_exceeded` | не повторяет, говорит, что в окне контекста не осталось места; раньше это была 502, и Codex отправлял те же данные ещё пять раз |
| `rate_limit_error` | `rate_limit_exceeded` | повторяет; ждёт столько, сколько названо в сообщении |
| `upstream_error`, `upstream_auth_error`, `upstream_timeout`, `service_unavailable`, `internal_error` | `server_error` | повторяет с собственной паузой 0,2 с × 2ⁿ (до 5 раз) |

Для лимита, который закончится не позже чем через 60 с, сообщение получает хвост
`Please try again in 20s.` в форме, которую разбирает Codex. Длиннее подсказки нет: Codex
выдерживает названную паузу целиком перед каждым из своих пяти повторов, верхней границы у
него нет (живая проверка: с подсказкой 900 с он через 25 с всё ещё спал). Без подсказки
запросы идут быстро и мгновенно получают тот же отказ, пока все аккаунты в лимите (до
апстрима они не доходят и ничего не стоят), и Codex печатает сообщение с оставшимся
временем. Живая проверка codex-cli 0.164.0 (запросов к relay до исправления → после):
невалидный structured-ответ, `prompt_too_large`, поздний 422 и нехватка кредитов — 6 → 1;
сбой upstream — 6 → 6, но с настоящей причиной вместо «stream closed before
response.completed». Официальный `openai` SDK (2.41.0 и 3.46.0) получает оба события и
чисто завершает поток; `responses.stream().get_final_response()` по-прежнему бросает
`RuntimeError`, потому что `response.completed` не приходил.
## Ограничения (важно)

- Retool на прямом транспорте (`copilotStreamGPT`) принимает клиентские инструменты
  (`tools`) нативно, транслируя их в JSON-схему upstream. Модель инициирует вызовы инструментов
  через нативные события `content_block_start` (`type: "tool_call"`) и `partialInputs`,
  без необходимости текстового бриджинга `<tool_call>` для объявлений и новых вызовов.
  Для продолжения принятой истории сохраняются исходные assistant/tool blocks
  и непрозрачные thinking signatures. Смена инструкций, модели, инструментов или
  аккаунта сбрасывает несовместимый подписанный prefix.
- Изображения (Vision) поддерживаются для мультимодальных моделей (Claude Opus 5.5,
  Sonnet 5, GPT-5.5 и др.) через OpenAI `image_url` и Anthropic `image` блоки. В каталоге
  `/v1/models` для них выставлен флаг `vision: true`. Картинку по http(s)-ссылке (`image_url`, `input_image`,
  Anthropic `image` с `source.type: "url"`) relay скачивает сам, один раз за запрос, только с публичного адреса
  и не больше 10 МБ. Картинку из Files API Anthropic (`source.type: "file"`) relay передать не может: ответ 422
  называет тип источника.
- Файлы (PDF и другие) до модели не доходят: у маршрута Retool нет блока файла, а в relay нет библиотеки,
  которая достала бы текст из PDF (замеры a4 от 2026-11-06: 0 из 11 PDF прочитаны во всех диалектах). Текстовый
  файл (`text/*`, JSON, XML в `data:` URL Chat `file` и Responses `input_file`) передаётся текстом. Всё остальное
  (Anthropic `document`, Chat `file`, Responses `input_file`) заменяется пометкой в скобках с именем, типом и
  размером, которая прямо говорит, что содержимое прочитать нельзя, и что модели делать: для файла, пришедшего
  внутри запроса, — не искать его (на диске его нет) и сказать пользователю; для `document` из локального Read —
  не читать тем же инструментом заново и один раз попробовать другой инструмент клиента. Раньше пометкой были
  200 символов JSON: модель принимала её за потерянные данные, гоняла инструмент по кругу или искала файл на
  машине relay через exec, а разговор навсегда становился плоским текстом. Теперь история остаётся нативной.
  Чтобы PDF читались, клиент должен прислать текст или в relay нужна библиотека (например, `pypdf`, чистый Python).
- Лимиты токенов вывода (`max_tokens`, `max_output_tokens`): если клиент запрашивает
  больше аппаратного максимума модели, relay мягко ограничивает (clamps) значение
  до допустимого максимума модели вместо отклонения с ошибкой 422. Маршрут Claude лимит не
  соблюдает, поэтому небольшой лимит (меньше 16 384) relay держит сам: см. «Ограничения
  маршрута Retool, которые relay обходит» ниже.
- Prompt Caching: инструкции и контекст проекта кэшируются (`openAICacheKey`, `cache: true`).
  При попадании в кэш повторные запросы оплачивают чтение вместо новой записи префикса.
  Фоновый keepwarm каждые 240 с продлевает кэш, в том числе у родителя работающего
  субагента. Первый пинг активного хода идёт на `cache_keepwarm_turn_offset`
  (по умолчанию 200 с, значение ограничено диапазоном [30, 275]; интервал
  `cache_keepwarm_seconds` тоже не больше 275 с: пинг, который не успел бы в окно кэша
  из списка ниже, не планируется. Админка даёт задать не больше 275 с в обоих полях, а большее значение из
  `config.json` relay сам урезает до 275 с); пять неудачных пингов подряд
  останавливают цикл (`failures`), но при настройках по умолчанию (интервал 240 с) до этого не доходит: повтор
  неудачного пинга идёт через 10, 20, 40 и 80 с после неудач и только пока он успевает начаться в окне кэша,
  поэтому цикл обычно останавливается раньше, как `cache_expired` с `after_failure`; все пять попыток помещаются
  в окно лишь при интервале около 130 с и меньше. Прогрев тоже оплачивается; попадание
  подтверждается только телеметрией upstream. Перезапуск relay сам по себе новой записи
  префикса не требует: диалог возвращается на свой аккаунт с прежней подписанной историей
  (см. «Состояние диалогов после перезапуска»). Но кэш живёт минуты, а остановленный relay
  его не греет: если от последнего касания кэша до следующего запроса прошло больше его
  срока жизни, префикс запишется заново и при перезапуске. Ошибки прогрева или недоступность
  аккаунта диалога тоже могут потребовать новой записи.
  Прогрев читает поток до `end_of_stream`, включая поздние usage после длинного
  thinking. Ошибка прогрева видна красной строкой `[err]` в консоли и в журнале;
  неподтверждённый прогрев не означает сохранённый кэш.
  Пинг — это последнее тело запроса плюс ещё одно сообщение пользователя без метки кэша:
  «это проверка связи, сразу ответь одним словом OK, не раздумывая, и не вызывай инструментов»
  (`direct.KEEPWARM_NUDGE`). Раньше пинг
  отправлял тело ещё раз, маршрут Claude игнорирует `maxCompletionTokens`, и модель заново
  писала весь прежний ответ: 1041 пинг стоил 467 кредитов вместо ожидаемых 194. Токен ответа
  стоит в 50–100 раз дороже токена, прочитанного из кэша. Теперь пинг читает тот же кэш (метки
  прежних сообщений не тронуты, `rit` пересчитан) и платит за чтение и несколько токенов ответа:
  на Sonnet 5.5 4 токена и 0,057 кредита вместо 715 токенов и 0,198; на Opus 5.5 с `high` 50
  токенов вместо 1505, с `max` около 150–370 (модель немного думает и над этим). Effort пинга
  остаётся прежним. Просьба не раздумывать вдвое сокращает это размышление: на Opus 5.5 с `max`
  медиана 190 → около 95 токенов, с `high` 54 → 36, на Sonnet без изменений (4 и около 80).

  Запросы, которые уходят одновременно с одной и той же «головой» (инструменты и system), которую
  никто ещё не закэшировал (Claude Code запускает несколько субагентов одного вида одним сообщением,
  у каждого одинаковая голова на 23 тыс. токенов), раньше записывали её каждый: около 1,1 кредита на
  каждого лишнего агента. Запись в кэше читается, только когда ответ, который её пишет, уже начался.
  Теперь первый из них идёт сразу, остальные ждут начала его ответа (не дольше 10 с) и читают голову
  из кэша; в журнале `cache.head_wait` с временем ожидания. Голова, которой пользовались последние
  270 с, считается закэшированной, и никто не ждёт.

  Метки кэша клиента (`cache_control` на текстовых блоках) relay раньше не читал: сообщение из нескольких
  блоков склеивалось в один текст с одной меткой в самом конце. Классификатор Auto mode (`auto-mode-check`)
  шлёт весь транскрипт одним user-сообщением из N текстовых блоков и ставит метки на два последних стабильных
  блока; после них идёт то, что меняется каждый раз (проверяемое действие и инструкция). Метка в конце
  этого текста не читалась никем, и каждая проверка заново записывала транскрипт: в живом сеансе Desktop 35
  проверок стоили 107 кредитов, по 28 тыс. токенов записи на проверку, при том что 64,7 тыс. токенов
  системного промпта читались из кэша. Теперь запрос **без инструментов**, у которого user-сообщение состоит
  только из текстовых блоков и помечен блок, не последний в нём, остаётся списком блоков, а метку получает
  последний помеченный блок. Метка одна на сообщение: upstream принимал её на не последнем блоке сообщения,
  но двух в одном сообщении не встречал (реплей даёт те же 186 кредитов с одной меткой, что и с двумя).
  Текст блоков тот же, что давала склейка: роль перед первым блоком, перевод строки между блоками, пустые
  блоки пропущены, блок из одних пробелов присоединён к предыдущему (Anthropic API не принимает текстовый блок
  без непробельных символов), пробелы
  в конце всего сообщения отрезаны. Поэтому текст для модели, `parsed.prompt` и отпечатки сообщений, по
  которым native-история сверяет диалог, не меняются ни на байт (292 из 292 настоящих тел классификатора,
  в 286 метка встала на последнюю метку клиента, после неё два блока хвоста). Реплей этих 292 тел на модели
  кэша провайдера: 359,6 кредита до, 186,2 после (a4). Запросы с инструментами, сообщения с изображением или
  `tool_result`, без метки и с меткой на последнем блоке идут прежним путём.

  Результат инструмента раньше метки кэша не получал: `native_history.cache_messages` пропускал сообщения, у которых
  `content` — словарь, а так хранятся результаты. Новый результат оплачивался как обычный ввод, когда приходил, и
  записывался в кэш только следующим запросом, у которого новейшая метка стояла уже после него: 43 703 токена
  обычного ввода (c6f288ce) и затем запись 43 918 токенов (26b9fe10); в диалоге OpenCode на Opus обычный ввод
  составил 14,9 из 224,7 кредита (6,6 %) (a3, 2026-11-06). Теперь на маршруте Anthropic (там метки — это брейкпоинты;
  остальные модели кэшируют сами) новейшая метка стоит на результате там, где он пришёл: он записывается один раз, а
  следующий запрос его читает. Текстовый результат становится списком из одного блока `text` с `cache: true`, у
  результата-списка метку получает его последний текстовый блок, результат без текста (одна картинка, пустая строка)
  метки не получает; форма уже отправленного результата не меняется, метка прошлого запроса остаётся вторым якорем,
  а всего меток не больше трёх (четвёртую upstream держит сам для tools). Сжатие метку на своей инструкции не ставит,
  но читает результаты чата. Upstream метку внутри результата инструмента не принимал ни разу, поэтому у неё есть
  страховка: HTTP 400 или 422, текст которого называет кэш или ничего не называет («Invalid request format», пустое
  тело), повторяется один раз без таких меток, и если повтор принят, до перезапуска их больше нет
  (`upstream.tool_result_hint_refused`, warn). Отказ, который называет другую причину (подпись или thinking, слишком
  длинный запрос, схема инструмента, фильтр содержимого), и ошибка сервера не повторяются. Что upstream принимает, но
  молча игнорирует, так не поймать: после перезапуска это видно по чтению кэша следующего запроса.

  Прогрев не тратит кредиты впустую: греется только то, к чему клиент может вернуться, и
  пинг уходит, только пока он ещё способен прочитать кэш. Кэш Anthropic живёт 5 минут
  (`PROMPT_CACHE_TTL = 300` с в `direct.py`), и срок отсчитывается от **начала** запроса,
  который запись последний раз записал или прочитал; чтение продлевает запись без доплаты
  ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).
  Пинг, пришедший после срока, ничего не продлевает: он оплачивает полную перезапись
  префикса, а она дороже чтения в 25 раз у Opus 5.5 и в 12,5 раза у Sonnet 5.5 (цены ниже). Правила,
  одинаковые для простаивающего диалога
  и для прогрева во время хода (`cache_keepwarm_during_turns`):
  - телом прогрева становится только ход с пригодным ответом: непустой текст или вызов
    инструмента, пришедшие в потоке, который дошёл до `end_of_stream`. Пустой ответ,
    «только thinking», оборванный поток, ошибка (в том числе тело, которое upstream
    отклонил) и отменённый ход не становятся телом прогрева и не сдвигают отсчёт срока:
    тело и отсчёт остаются от последнего удачного хода. Цикл прогрева останавливается
    с причиной `last_turn_failed` (`turn_outcome` — как закончился ход: `empty`,
    `thinking_only`, `truncated`, `error`, `rejected`, `cancelled`) и начинается заново
    только со следующим удачным ходом; разбор исхода тот же, что у трассы попыток
    (`direct.attempt_outcome`);
  - пинг не отправляется, если последнее подтверждённое касание кэша (начало настоящего
    запроса или начало удачного пинга; внутри хода это начало самого хода) старше
    `PROMPT_CACHE_TTL - PROMPT_CACHE_MARGIN` = 300 − 20 = 280 с: цикл останавливается
    с причиной `cache_expired`. Запас в 20 с покрывает такт планировщика, ожидание рабочего
    потока и дорогу до провайдера. Тем же правилом ход, шедший дольше окна без удачного
    пинга (прогрев во время хода выключен или не удался), не оставляет после себя пингов.
    Между ходами цикл не запускается вовсе для диалога, чей последний ход неудачен или
    чей кэш уже истёк (пул запускает цикл заново на каждый запрос дочернего диалога, и
    остановка не должна повторяться на каждый из них);
  - неудачный пинг (таймаут, исключение, поток без `end_of_stream`) касанием не считается:
    его результат неизвестен. Повтор идёт через 10, 20, 40 с и так далее, но только если
    успевает начаться в том же окне от последнего подтверждённого касания; иначе цикл
    останавливается с `cache_expired` (в событии `after_failure`);
  - пинг, чей usage показал запись вместо чтения, останавливает цикл с причиной
    `cache_rewritten` (уровень `warn`), и потеря ограничена одной перезаписью на сессию: метка держится на
    сессии, а не на цикле, поэтому до следующего удачного хода диалога новый цикл не запускается (ни по запросу
    дочернего диалога, ни внутри идущего хода). Перезаписью
    считается `promptTokensWrittenToCache` не меньше 50 000 токенов (порог консольной метки
    `[WRITE HIGH]`; по цене записи Opus 5.5 это 5 кредитов, как у шести обычных пингов префикса в
    190 тыс. токенов) или не меньше половины кэшируемого префикса (`promptTokensReadFromCache`
    + записанное; так ловится промах на небольшом промпте). Запись меньше 1024 токенов — шум.
    Здоровый пинг читает префикс и почти ничего не пишет: его тело то же, что у прошлого хода.

  Прогрев простаивающего диалога (без идущего хода) ограничен по времени, и эти
  пределы не зависят от учёта пула:
  - основной диалог греется `cache_keepwarm_idle` (900 с) после последнего настоящего
    запроса клиента; сами пинги срок не продлевают;
  - субагент (диалог с родителем), чей последний ответ закончился вызовом инструмента,
    греется `cache_keepwarm_subagent_idle` (1800 с): клиент выполнит инструмент и вернётся;
    `0` отключает прогрев субагентов между ходами;
  - субагент, ответивший без вызова инструмента, отдал результат: прогрев останавливается
    сразу;
  - аккаунт, который выключен или исключён диспетчером из маршрутизации (признак
    `backend.unavailable`: баланс ниже `min_account_balance`, нужен новый вход или любая
    другая причина), получает только запросы клиента. Прогрев не сверяется со списком
    причин, поэтому причина, добавленная позже, действует на него сразу;
  - диалог, вытесненный из пула, больше не прогревается. По простою (`conversation_idle_timeout`)
    пул закрывает диалог только после конца его прогрева; прогреваемый диалог может вытеснить
    лишь нехватка места, и то после всех диалогов без прогрева.

  Родитель остаётся тёплым, пока жив запрос его дочернего диалога: ход не дольше
  `turn_timeout` или любая активность ребёнка в пределах его лимита. Когда запрос ребёнка
  закончился, родитель остаётся тёплым, пока ребёнка ждут обратно: тот ещё не дал окончательного ответа
  (его ответ попросил инструмент, например долгий прогон тестов) или его собственный прогрев ещё идёт,
  и с его последнего запроса прошло не больше `cache_keepwarm_subagent_idle`. Так субагент, который
  20 минут ждёт тестов, возвращается к тёплому родителю; раньше прогрев родителя кончался через
  `cache_keepwarm_idle` после конца запроса ребёнка, и родитель записывал весь префикс заново.
  Ребёнок, закрытый, отменённый или вытесненный из пула, родителя не держит. Потерянное
  освобождение (счётчик зависимых навсегда больше нуля) и ход, занятый дольше
  `turn_timeout`, прогрев не продлевают: для ходов дольше 900 с увеличьте `turn_timeout`.
  Прогрев внутри идущего хода не ограничивается лимитами простоя и продолжается при любом
  состоянии аккаунта, но не дольше `turn_timeout` от начала хода.

  Значения выбраны по цене. Пинг читает кэш префикса (`4e-6` кредита за токен у Opus 5.5 и Sonnet 5.5), промах
  записывает его заново: `1e-4` у Opus 5.5 (в 25 раз дороже чтения) и `5e-5` у Sonnet 5.5 (в 12,5 раза). Для
  префикса в 190 тыс. токенов это 0,76 кредита за пинг и 19 кредитов за промах у Opus, 9,5 кредита за промах у
  Sonnet. Цены подтверждены журналом живого relay (подгонка по ходам совпала с учётом в пределах округления):
  чтение `4e-6` у обеих моделей, запись `1e-4` у Opus 5.5 и `5e-5` у Sonnet 5.5. `credits.py` хранит ставки
  каждой измеренной модели (`MODEL_RATES`): Opus 5.5 и Sonnet 5.5 (вход `8e-5` / `4e-5`, вывод `4e-4` / `2e-4`),
  gpt-6.1-sol (вход `4e-5`, чтение `2e-6`, запись `5e-5`, вывод `2e-4`), gpt-6.1-terra (вдвое дешевле sol), gpt-5.5,
  claude-sonnet-5, GLM-5.3 (вход `1.12e-4`, чтение `1.12e-5`, вывод `3.52e-4`) и GLM-5.3-Flash (`6e-5`, `1.2e-5`,
  `2e-4`). GLM и gpt-5.5 не сообщают о записи в кэш: непрочитанный префикс оплачивается у них как обычный вход,
  поэтому их `cache_write` равен цене входа. По ставкам модели хода считаются оценка прогрева и поля `cost_*`
  события `upstream.usage`, остальные модели берут прежнюю общую подгонку (`RATE_CACHE_READ`,
  `RATE_CACHE_WRITE`). Настоящую цену хода несёт `credits`. Субагент, чей ответ попросил
  инструмент, ждёт его результата и возвращается почти всегда: в журнале за 20 часов (6–7 ноября

  1800 с: до семи пингов покрывают инструмент длиной около получаса, и даже субагент, который так
  и не вернётся, обходится дешевле одной перезаписи префикса (по ставкам Claude, GPT и GLM-5.3).
  Для основного диалога каждые лишние 15 минут прогрева —
  3,75 пинга (≈2,9 кредита) на каждый заброшенный диалог; это окупается, только если
  больше 15% простоев, дошедших до 15 минут, заканчиваются в следующие 15. Журнал живого
  relay за 20 часов (6–7 ноября 2026) показал меньше 1%: из 284 основных диалогов, чей прогрев

  перезаписи префикса (до 96 минут у Opus и gpt-6.1-sol), добавил бы около 283 кредитов
  пингов диалогам, к которым никто не вернулся, и сберёг бы около одного; почти все такие
  диалоги — разовые прогоны агентов, и по истории диалога их не отличить. Пул не закрывает
  диалог, пока идёт его прогрев, поэтому для длинных пауз достаточно поднять
  `cache_keepwarm_idle`.
  Остановка пишется в журнал событием `cache.keepwarm_stop`: `reason` (`idle_limit`,
  `subagent_done`, `account_unavailable`, `evicted`, `failures`, `last_turn_failed`,
  `cache_expired`, `cache_rewritten`, `compacted`; `closed` — сессию закрыли
  после уже отправленных пингов), `pings` и `idle_pings` цикла, `credits` — списанное этими
  пингами (известная часть), `idle_seconds` с последнего настоящего запроса, применённый
  `limit`, `subagent`, `account` и названия диалога. У `account_unavailable` есть
  `account_state`: `disabled` или причина из `backend.unavailable` (`exhausted`,
  `auth_dead` и другие), у `failures` — `failures`. У `last_turn_failed` есть
  `turn_outcome`. У `cache_expired` есть `touch_age_seconds` (возраст последнего
  подтверждённого касания в момент решения), `limit` (окно, 280 с), `during_turn` и, когда
  повтор неудачного пинга не успевал в окно, `after_failure` с `failures`. У `cache_rewritten`
  (уровень `warn`) есть `written_tokens`, `read_tokens`, `prefix_tokens`, `ping_credits` —
  цена перезаписавшего пинга — и `touch_age_seconds`. `compacted` — клиент сжал историю
  диалога: тело запроса сжатия не греется, а прежний префикс больше не продолжится.
  `cache_rewritten`, `last_turn_failed` и `compacted` держатся на сессии: новый цикл
  прогрева, в том числе по запросу дочернего диалога, начинается только после следующего
  удачного хода этого диалога. Событие `cache.keepwarm` каждого
  пинга тоже несёт `touch_age_seconds`; пинг, перезаписавший префикс, пишется уровнем `warn`.
  Разовые задачи Codex — запрос без инструментов со строгой схемой ответа (извлечение памяти
  из старого треда) — не греются вовсе, не оставляют ветки, ничего не пишут в кэш сверх
  прочитанного и не трогают сессию, на которой идут; в журнале у них `client_task: background`.
- Сжатие истории клиентом (compaction). OpenCode 2.x (по исходникам каждого тега с v2.0.0 по v2.2.5) сжимает диалог
  так: шлёт запрос чата, с тем же system, теми же tools и той же историей, и одним сообщением user в конце с просьбой о
  сводке (оно начинается «You MUST summarize the conversation above…», для повторного сжатия — «Update the existing
  checkpoint…»; после ответа мимо шаблона добавляется ещё одно сообщение «The previous response did not fill in the
  required summary template…»; [исходник](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/core/src/session/compaction.ts)).
  Claude Code шлёт то же ([кэширование Claude Code](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation)),
  с заголовками `x-claude-code-request-class: compaction` и `x-claude-code-compaction`
  ([протокол](https://code.claude.com/docs/en/llm-gateway-protocol); на пользовательском base URL они приходят только при
  `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`), а его инструкция начинается «CRITICAL: Respond with TEXT ONLY. Do NOT call any
  tools.» (2.1.316; неофициальный [снимок запроса](https://clawdipedia.cc/prompts/context-and-memory/compact)) или, в
  более ранних версиях, «Your task is to create a detailed summary of the conversation so far». OpenCode 1.x сжимает
  отдельным запросом скрытого агента `compaction` без tools; сообщение начинается по версиям так (по всем тегам
  v1.0.144–v1.19.5): «Provide a detailed prompt for continuing our conversation above» (до v1.14.18), «When constructing
  the summary, try to stick to this template» (v1.14.19–v1.14.20), «Create a new anchored summary…» или «Update the
  anchored summary below…» (v1.14.21–v1.18.16), «Here is the conversation so far:» (v1.18.17–v1.19.5). Relay узнаёт
  сжатие по началу сообщения (весь текст не нужен: он меняется от релиза к релизу), по этим заголовкам, по имени агента
  `compaction` (плагин OpenCode 1.x), по явному `X-Proxi-Task: compaction`, по `x-codex-turn-metadata` Codex
  (`request_kind: compaction`) и по началу инструкции DeepSeek Harness («You are now acting as a compaction engine for this
  AI coding assistant.»: Harness сжимает самый старый кусок истории с тем же system, теми же tools и теми же первыми
  сообщениями чата, без заголовка и без идентификатора сессии; сводка такого запроса не греется: раньше его тело пинговали
  три раза, а Harness его больше не присылает). Метка `client_task: "compaction"` стоит у
  каждого события запроса в журнале (`turn.begin`, `upstream.usage`, `turn.end`, `native_history.*`), в консоли —
  `TASK: compaction`, в админке — «сжатие» у хода. `request_purpose`, повторы пустого ответа и профиль промпта от метки
  не зависят: сжатие идёт по профилю чата, иначе его head отличался бы от head чата и переписал бы кэш. Ответ сжатия
  ветку диалога не записывает: клиент подменяет историю сводкой и продолжать этот запрос не будет, а повтор сжатия (после
  напоминания про шаблон, повторный `/compact`) и сам чат после прерванного сжатия продолжаются с прежней ветки.

  Хвост запроса сжатия в кэш не пишется. Клиент подменяет историю сводкой, поэтому ни инструкцию сжатия, ни (у
  OpenCode 1.x, который склеивает весь диалог в одно сообщение) сам диалог никто больше не отправит, а метка кэша
  на хвосте заставляла провайдера записать его по цене записи: 98 956 токенов, 10,87 кредита, которые никто не
  прочитал, и ещё 33 308 токенов заново для первого обычного запроса (a3, 2026-11-06, 866b7de6 и 16e98d69). Теперь у
  последнего сообщения запроса сжатия нет метки (ни в тексте истории, ни в нативной). Метки на system и на части
  истории до него остаются: по ним сжатие, которое делит с чатом system, tools и историю (OpenCode 2.x,
  Claude Code), читает кэш чата.

  Дорогим сжатие делает смена effort. У скрытого агента `compaction` свой вариант (`agent.compaction.variant`;
  в 2.x это `#variant` у `agents.compaction.model`), и сводка идёт на `high`, пока чат работает на `max`. Effort
  входит в область подписанной ветки relay (`reasoningEffort`), поэтому запрос с другим effort начинает историю
  заново (`native_history.reset`, `native_history.cold`), а Anthropic при смене `output_config.effort` всё равно
  сбрасывает кэш сообщений ([кэширование](https://platform.claude.com/docs/en/build-with-claude/prompt-caching),
  строка «Effort setting»; [мышление и кэш](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost)).
  Живой случай 2026-11-05 (OpenCode 2.2.5, Sonnet 5.5, 540 тыс. токенов): обычный ход чата записывал около 1 тыс.
  токенов (3,5 кредита), сжатие записало 532 тыс. (28 кредитов); три сжатия подряд — 90,6 кредита.

  Сжатие Claude Desktop устроено иначе: это история его последнего запроса без ответа на него (клиент кладёт ответ
  в историю только следующего хода) и одно сообщение user с инструкцией после неё (в Messages оно в том же ходе, что
  результаты инструментов). Цепочка `History.resume` ждёт эхо ответа и такую форму не принимала никогда: история
  начиналась заново, и записывался весь префикс, хотя у провайдера он ещё лежал в кэше (a4, 2026-11-06: 485 тыс.
  токенов, 51,9 кредита за один `/compact`; на эмуляции с 130 тыс. токенов 6,61 кредита и 9,2 с до первого токена
  вместо 2,57 и 2,5 с). Для сжатия, и только для него, `History.resume_fork` отвечает на эту форму: история клиента
  должна совпасть с историей, из которой пошла ветка (то же `conversation`, `provider`, `head`, `tools`), а после неё
  идти только сообщения user. В upstream уходит собственный вход ветки (то, что кэшировал её запрос) плюс эти
  сообщения; ответ ветки не повторяется, поэтому подпись не прикладывается ни к чему, чему она не принадлежит. Сводка
  ветку не записывает. В журнале это `native_history.resume` с `fork: true` (и `blocks: 0`, `signatures: 0`); effort
  диалога берётся так же, как для хода диалога, и по тому же правилу «не ниже запрошенного».

  Сжатие Codex (локальное: у пользовательского провайдера оно всегда такое, исходники rust-v0.167.0,

  performing a CONTEXT CHECKPOINT COMPACTION…». Codex 0.167 сам называет такой запрос в `x-codex-turn-metadata`

  промпте (`compact_prompt` в config.toml заменяет шаблон). Инструменты стоят первыми в префиксе кэша провайдера, поэтому
  такой запрос не делил с чатом ничего: он шёл на отдельной сессии без нативной истории и записывал историю заново (Codex,

  истории и вызова не выполняет, поэтому ответ сжатия с вызовом инструмента до Codex не доходит (`summary_guard`,
  `direct._summary_stream`): попытка отбрасывается целиком (событие `turn.compaction_tool_call`, её стоимость

  сжатие Codex (`remote_compaction = "v2"` в `[model_providers.<id>.capabilities]`: запрос чата с элементом
  `compaction_trigger` в конце) relay не поддерживает и отвечает 422: включать его не нужно.

  При `compaction_keep_effort: true` (по умолчанию) relay запускает распознанное сжатие на effort диалога, если
  запрос действительно продолжает подписанную ветку этого диалога: тогда совпадают система, tools, модель, аккаунт и
  история (relay задаёт тот же вопрос, что и transport при resume), а effort допустим для модели по правилам, которым
  подчиняется effort клиента (приближённый уровень — другой префикс, он не подходит), и он не ниже effort, на котором
  пошёл бы сам запрос: relay никогда не понижает effort ради кэша (диалог на `low` не подставляется клиенту, который
  просит `high`: такое сжатие идёт на `high`, история записывается заново, причина — `lower`). Платится только хвост; подписи
  берутся из веток relay, не из запроса клиента. Журнал: `turn.begin` хранит `requested_effort` клиента,
  `effective_effort` диалога, `effort_source: dialog`, `effort_resolution: cache_continuity`; рядом пишется
  событие `cache.effort_kept`. Обычный ход, в том числе с effort, который пользователь сменил
  посреди диалога, relay не трогает. Если продолжать нечего (ветки нет: первый запрос или сохранённое состояние
  после перезапуска не применилось; другой system, tools или
  модели агента сжатия, у сжатия OpenCode 1.x, которое идёт запросом без tools, и у 2.x, когда диалог не помещается
  в окно и OpenCode шлёт укороченную историю или текст без tools), effort остаётся тем, что прислал клиент, а метка в
  журнале показывает, почему вызов дорог. Причину пишет событие
  `cache.compaction_restart`: `no_branch` (у диалога нет ветки: первый запрос, сохранённое состояние истекло, не
  применилось или его нет, другой аккаунт; сам перезапуск ветку не теряет, см. «Состояние диалогов после
  перезапуска»), `history` (сообщения запроса не продолжают ветку), `scope` и `differs` — чем запрос отличается от ветки
  (`provider` — модель или аккаунт, `head`, `tools`, `tool_choice`, `conversation`), `effort` (effort ветки не
  годится для модели) или `lower` (effort диалога ниже effort запроса). Чтобы не зависеть от relay, уберите запись `compaction` из `agent`/`agents` в `opencode.jsonc`:
  тогда OpenCode сжимает на модели и варианте самого чата; одного `variant` убрать мало, запись с моделью и без
  варианта идёт на уровне по умолчанию этой модели, а запись с другой моделью (Sonnet при чате на Opus) никогда не
  делит кэш с чатом ([настройка](docs/client-setup.md#compaction-and-the-effort-of-its-agent)).

  счётчики предыдущей попытки.
- Стоимость в админке (`/admin/api/metrics`, `/admin/api/turns`) считается по попыткам
  upstream. Неизвестной (`credits_unknown`) считается только попытка, которая сообщила
  usage без допустимой цены (конечное число не меньше 0; NaN, минус и один лишь флаг
  `credits_reported` ценой не являются) или которую клиент отменил до телеметрии.
  Прямой транспорт сообщает такую попытку пустым маркером usage; устаревший агентный
  транспорт (WebSocket) делает то же, когда попытка дала текст, thinking или вызов инструмента,
  а `run_credits_persisted` не пришёл (в том числе после таймаута): журнал и `usage` клиента
  называют её неизвестной одинаково, а не журнал «бесплатной», а адаптер «неизвестной».
  Ход, отклонённый до upstream (413, 402, 503), попытка с отказом по HTTP (429, 500)
  и запрос, не покинувший relay (DNS, отказ соединения, TLS), ничего не стоят; таймаут
  чтения или обрыв после отправки может быть оплачен и остаётся неизвестным. Идущий ход
  не делает окно неполным и виден в `credits_in_progress`. Стоимость прогрева кэша
  (`cache.keepwarm_usage`) входит в `credits` и отдельно в `keepwarm_credits`; прогрев
  без `actual_credits` неизвестен. В `/admin/api/turns` неизвестная цена — `null`, а не 0;
  `credits_complete` истинно только у завершённого хода без неизвестных попыток.
- Метаданные хранятся в `models.py`; локальная маршрутизация фильтрует известные
  несовместимые пути и условия ресурсов. Окончательное право доступа проверяет Retool.

### Ограничения маршрута Retool, которые relay обходит

Часть параметров маршрут Retool у моделей Claude отвергает или молча не выполняет. Relay делает это сам; GPT и GLM
принимают те же параметры, и их запросы он не меняет.

**Принудительный вызов инструмента** (`tool_choice`: `required`, `any` или имя инструмента). Retool отвечает на него
`400 tool_choice: type "tool" and "any" are not supported for this model` для каждой модели Claude, при любом effort, с
thinking и без. Клиенты, которые требуют вызов (структурированный вывод через инструмент, Agents SDK, LangChain), на Claude не
работали. Теперь relay отправляет Retool `auto`, а в конец запроса добавляет одно user-сообщение с просьбой:

> Call the tool `<имя>` now, and no other tool; do not answer in text. If a required argument is unknown, use a plausible value instead of asking.

Для `required` просьба начинается «Call one of the available tools now; do not answer in text.». Сообщение стоит последним
только в запросе к Retool: без метки кэша, вне сохранённой истории и вне `tool_choice` подписанной ветки. Поэтому префикс,
подписанное мышление и кэш следующего запроса те же, что без эмуляции, и следующий запрос продолжает ветку, даже когда клиент
уже ничего не требует (`native_history.resume`). Оговорка: подпись мышления выдана в запросе с этой просьбой, а
возвращается без неё; приняла ли Retool такую подпись, живой проверкой ещё не подтверждено.

Ответ попытки удерживается, пока в нём нет нужного вызова: текст и thinking попытки без вызова клиенту не уходят. Вызовы
других инструментов при именованном выборе клиенту не передаются (журнал: `tool.call_dropped`). Если вызова нет, relay один раз
повторяет запрос с более жёсткой просьбой («IMPORTANT: your next message must be a call to the tool `<имя>`, and no other
tool. Do not write any text, do not ask questions and do not refuse; call it now. …»; журнал: `turn.forced_choice_missed`,
`warn`). Если вызова нет и после повтора, клиент получает `502 upstream_tool_choice_ignored` (после текста или вызова другого
инструмента) либо `upstream_empty_turn` (после пустого ответа). Оплачиваются обе попытки. Ответ с эмуляцией несёт заголовок
`x-proxi-tool-choice: emulated`.

Замеры 2026-11-06 (532 попытки, Opus 5.5 и Sonnet 5.5, thinking включён и выключен, от одного до трёх небольших
инструментов): `auto` без просьбы вызвал нужный инструмент в 0 из 10 по каждому из пяти случаев, где запрос к нему не ведёт;
простая просьба («Call the tool X now; do not answer in text.») — в 210 из 240, при этом модель не придумывала
недостающий аргумент (спрашивала город) и при именованном выборе вызывала ещё и другой инструмент; формулировка выше — в 160 из
160, без лишних вызовов и без текста перед вызовом. Обе формулировки, как их собирает код relay (основная и жёсткая
для повтора), проверены ещё раз как единственная просьба в запросе к живому relay (4 случая × 2 модели × thinking вкл/выкл ×
3 попытки): по 48 из 48. Не замерено: запросы с десятками инструментов и сотнями тысяч токенов (Desktop) и поток (SSE).

**Лимит длины ответа** (`max_tokens` в Chat и Messages, `max_completion_tokens`, `max_output_tokens` в Responses). Маршрут
Claude принимает `maxCompletionTokens` и не соблюдает: при лимите 300 токенов пришло 5 466 с `end_turn` (протокольный прогон
2026-11-06; при лимитах 16, 64 и 300 — от 838 до 1 028 токенов, во всех трёх диалектах). GPT и GLM лимит соблюдают, их ответ
relay не режет. Ответ Claude relay обрезает сам, как это делает провайдер: на лимите ответ кончается, клиент получает
`stop_reason: "max_tokens"` (Messages), `finish_reason: "length"` (Chat) или статус `incomplete` с
`incomplete_details.reason: "max_output_tokens"` (Responses; событие `response.incomplete`).

Что считается: текст, который получает клиент, и вызов инструмента по его имени и аргументам (оценка: около 3,5 символа
ASCII и 2 прочих символа на токен; точного токенизатора у relay нет). Мышление не считается: маршрут скрывает его
большую часть, и лимит, потраченный на него, превратил бы маленький лимит в пустой ответ. Текст обрывается там, где
кончается лимит. Вызов инструмента клиент получает целиком или никак: события вызова ждут, пока upstream не закончит
его, а вызов, который не влезает, отбрасывается вместе со всем, что идёт после него, — половины вызова в потоке нет. Генерация
у провайдера при этом не прерывается: токены сверх лимита оплачены, а `usage` и стоимость остаются такими, какими их сообщил
upstream (клиент видит 5 466 токенов при лимите 300). Журнал: `reply.cut_at_cap` (лимит, сколько токенов получил клиент,
сколько вызовов отброшено). Ответ, который обрезан, а клиент потом присылает назад, не совпадёт с сохранённой веткой и
пойдёт без неё, как после стоп-строки; а JSON-формат, оборванный лимитом, даёт `502 upstream_invalid_output` с
«the reply was cut short (length)», не битый документ.

Порог: лимит держится только ниже 16 384 токенов (`generation.OUTPUT_CAP_EMULATED_BELOW`). Ответы маршрута сами заканчиваются
через несколько тысяч токенов, поэтому такой лимит не сработал бы, а держать вызов клиента до конца ради лимита, который
клиенты задают 32 000–128 000 (Claude Code, Desktop, OpenCode), значило бы лишить их потоковых аргументов на каждом вызове.

**WebSearch** (Claude Code). Поиск Claude Code — серверный инструмент провайдера `web_search_20250305` (так же версии
`web_search_20260209` и `web_search_20260318`): Anthropic выполняет его сам, а маршрут Retool умеет только клиентские
инструменты, поэтому relay отвечал на такой запрос `422`. С настроенным поиском relay выполняет его сам. В `config.json`:
`"web_search_provider": "exa"`, а ключ Exa лежит в переменной окружения процесса relay, имя которой задаёт
`web_search_key_env` (по умолчанию `EXA_API_KEY`); в `config.json` ключа нет, и relay маскирует его значение во всех
сообщениях, как cookie. Без провайдера или без ключа в переменной ответ прежний (`422` с подсказкой про эти настройки), а при
запуске relay предупреждает. Остальные настройки: `web_search_endpoint` (`https://api.exa.ai`), `web_search_results`
(5 страниц на поиск), `web_search_timeout` (20 с); меняются после перезапуска.

Как это работает. Инструмент объявляется модели обычной функцией `web_search(query)`. Когда модель вызывает её, relay ищет
на Exa (`POST /search`, ключ в `x-api-key`), отдаёт результаты модели текстом (название, адрес, дата, найденные фрагменты) и
продолжает ответ с того места, где он остановился: подписанное мышление, вызов и результат уходят в Retool нативно, тем же
путём, каким клиент продолжает свой цикл инструментов, а кэшированное начало запроса не меняется. Клиент получает ответ в
формате Anthropic: блоки `server_tool_use` и `web_search_tool_result` (поток показывает вызов, пока он пишется, а результат
приходит целиком в `content_block_start`, как у Anthropic) и `usage.server_tool_use.web_search_requests`, поэтому Claude Code
показывает поиск так же, как с настоящим API. `encrypted_content` — непрозрачная строка с текстом страницы (шифрования нет:
клиент возвращает её в истории, и по ней relay восстанавливает то, что читала модель). `max_uses` (10, если инструмент его не
задал) считает каждый вызов, удачный или нет; вызовы сверх лимита получают результат-ошибку `max_uses_exceeded`, и модель
отвечает по тому, что есть. Ошибки поиска (`too_many_requests`, `invalid_tool_input`, `query_too_long`, `unavailable`) — тоже
результаты-ошибки, ход они не обрывают; неудачный поиск не считается в `web_search_requests`. `allowed_domains` и
`blocked_domains` передаются Exa (`includeDomains` / `excludeDomains`, с поддоменами) и ещё раз проверяются в relay, что бы ни
вернул провайдер. Цикл ограничен: после `max_uses` модели дают ещё два хода, потом ответ заканчивается
(`web_search.loop_stopped`).

История. Запрос, где поиск — единственный инструмент (так Claude Code вызывает WebSearch: отдельным запросом с id того чата,
которому он служит), идёт отдельной задачей: он не берёт сессию чата, не меняет её head, tools и подписанную ветку.
Запрос, где у клиента есть свои инструменты, идёт в сессию диалога, и ответ, который клиент вернул целиком, продолжает ту же
подписанную историю (`native_history.resume`): `server_tool_use` и `web_search_tool_result` читаются как вызов и его результат.
Если модель в одном ходе вызвала и поиск, и инструмент клиента, relay выполняет поиск, ход заканчивается вызовом инструмента
клиента (`stop_reason: tool_use`), а результат поиска идёт в том же сообщении. Журнал: `web_search.run` (запрос, число
результатов, мс, код ошибки; ключа в нём нет) и `web_searches` в `turn.end`.

Чего нет. Цитат (`citations` у текстовых блоков) relay не создаёт: модель называет источники в тексте. Токены в `usage` — как у
любого запроса из нескольких шагов: числа последнего шага, а кредиты суммируются. Каждый поиск — это ещё один платный запрос к
Retool плюс запрос к Exa. `web_fetch`, `code_execution` и прочие серверные инструменты отклоняются, как раньше; динамическая
фильтрация, `allowed_callers` и `response_inclusion` новых версий инструмента не применяются; только диалект Anthropic.

**GLM-5.3: ограничение частоты, первый токен, effort.** Retool отвечает на запросы к GLM `429 Retool models are rate limited
right now. Please try again shortly.`; первый токен приходит через 2–55 с; уровень рассуждения GLM принимает и не учитывает. Что
relay с этим делает. 429 приходит до начала генерации (ошибкой в потоке внутри ответа 200 или статусом HTTP), поэтому он
бесплатен и повтор безопасен: relay ждёт несколько секунд и отправляет то же тело ещё раз на том же аккаунте, до
`upstream_rate_limit_retries` раз (3 по умолчанию; паузы около 2, 4 и 8 с, считая задержку между POST шага; не больше 5 POST на
шаг; журнал: `upstream.rate_limited`). Ответ после повтора целый, цена известна: отказ её не портит. Повтор не делается, если
ответ уже пошёл к клиенту, для часового лимита аккаунта (он выводит аккаунт из пула, как раньше) и для других ошибок. Если
лимит не снялся, клиент получает тот же `429` с `Retry-After: 1` и числом попыток в `upstream_attempts`.

Чего relay сделать не может. Он не переводит диалог на другой аккаунт при таком 429: история модели и кэш там начались бы
заново (79 тыс. токенов в измеренном случае), а убежищем другой аккаунт не был: в протокольном прогоне 2026-11-06 четыре разных
аккаунта получили этот 429 в пределах двух минут. Он не ставит запросы в локальную очередь: бюджета Retool он не знает.
Он не ускоряет первый токен и не укорачивает сам лимит: очередь и лимит на стороне Retool. Пока идёт ожидание, потоковый клиент
видит только keep-alive. Effort у GLM остаётся «принимается, не передаётся» (`reasoning_effort_control: accepted-ignored`, каталог
не предлагает уровней): выбор уровня на скорость и глубину ответа не влияет, и это записано в метаданных модели.

## Что проверено вживую (Retool, свежая сессия)

- все три диалекта в streaming и non-streaming возвращают реальный ответ модели;
- маршрутизация провайдеров: `claude-opus-4-8` → Anthropic, `gpt-5.5` → OpenAI;
- два параллельных запроса создают два треда и не видят историю друг друга;
- allowlisted-команда (`dir`) исполняется локально, неразрешённая (`whoami`) даёт код 126
  и текст политики, аудит пишется в `commands.log`;
- пустые ходы диагностируются: исчерпание кредитов отдаётся как `402 insufficient_credits`
  (по балансу аккаунтов), а не пустой `200`; пустой ответ сам по себе даёт
  `502 upstream_empty_turn`;
- upstream 401 при мёртвой сессии отдаётся как `502 upstream_auth_error` после попытки refresh.
