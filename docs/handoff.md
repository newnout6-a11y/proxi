# Передача контекста: работа по прямому транспорту relay

Состояние на момент передачи. Всё ниже — либо проверено в сессии, либо помечено как непроверенное.

## Проект

`C:\specialinay_papka` — локальный HTTP-relay над внутренним WebSocket-протоколом Retool AI Agent.
Даёт OpenAI/Anthropic-совместимый доступ к моделям организации. Ветка `codex/relay-hardening-native-tools`.
Прокси слушает `127.0.0.1:8787`, ключ в `relay_key.txt`, супервизор `scripts/run_relay.ps1` (pid в `relay.pid`).

## Задача была

Прямой бекенд (найден ранее, `docs/direct-inference-audit.md`) отвечал за ~1,5 с, но без проектного
контекста. Требовалось получить ту же скорость **вместе с передачей контекста**, а не вместо неё.

## Что выяснено про бекенд

- `POST /api/gpt/copilotStreamGPT?origin=frontend`: cookie + `x-xsrf-token`, обязательный `rit`
  (некриптографический хеш длин JSON), NDJSON в ответ.
- `metadata.sandpackAgent: true` переключает на список App Builder: доступны Opus 5.5/5/4.8/4.7/4.6/4.5,
  Sonnet 5.5/5, GPT-5.4/5.5/5.6, GPT-6 Sol, GPT-6.1 Sol, GLM-5.3. Без маркера — список Assist:
  Sonnet 5/4.6/4.5, Haiku 4.5, GPT-5 семейство. Официальная матрица Retool помечает Opus 5.5 как
  недоступный на managed-ключе в обоих контекстах — работает по факту.
- **Кэш**: блок `text` принимает `cache: true`, запрос — `openAICacheKey`. Повторный ход читает префикс:
  100 000 символов контекста, второй прогон — 17 входных токенов вместо 32 504 и 0,133 кредита вместо 3,25.
  `ttl` блока бекенд **не** принимает (400). Провайдерский кэш живёт минуты.
- Форма промпта: инструкции и контекст — `system`, реплика клиента — `user`. Маркеры
  `[CLIENT CONVERSATION — chronological]` и `[CONTINUE THE CURRENT CLIENT TURN]` на этом пути дают пустые
  ходы (с длинным тире 8/8, с ASCII-дефисом 0/6) — прямой транспорт их не добавляет.
- Найдены и добавлены в каталог: `claude-sonnet-5-5` (работает). `claude-haiku-5-5`/`claude-haiku-5`
  бекенд не знает (400 на обоих списках).

## Что реализовано в коде

Новый транспорт по умолчанию `direct` (флаг `transport`, `direct` | `agent`):

- `direct.py` — `make_rit`, конвертер JSON Schema → формат Retool, `build_body` с кэш-блоками,
  разбор NDJSON, сборка вызовов по `toolCallId`, приведение «строковых» чисел к типу схемы,
  один повтор на пустой ход, подтяжка effort, ретрай на Assist-список.
- `session.py` — `Backend.headers()`/`new_thread_id()`, `RelaySession.set_direct()`, ветка в `_stream_turn`.
- `orchestrator.py` — инструкции уходят system-блоком, история чанками, фолбэк на WS.
- `proxy.py` — `POST /v1/messages/count_tokens`, сброс протухшего статуса в логе.
- `models.py` / `validate.py` — `resolve_tolerant`: неподдерживаемый effort подтягивается к ближайшему.
- `adapters.py` — оценка токенов считается по реально отправленному промпту.
- Кэш истории: точка кэша переносится на конец истории каждый ход. Урезан `context_max_bytes` 120000 → 40000.
- `cache_keepwarm_seconds` (240): пока диалог активен, префикс перечитывается, чтобы кэш не истёк.
  Проверено: пауза 80 с → три пинга → ход с `write=19` вместо 143 441.

## Открытый вопрос на момент передачи

Пользователь сообщает, что после серии ходов снова стало медленно (последние замеры 7,6–13,7 с на ход).
Что уже установлено: голова промпта стабильна (sha совпадает между вызовами, 354 символа для клиентов с инструментами),
`/health` — 200. Причина не локализована.

Гипотезы по убыванию правдоподобия:

1. Сессия ~158 000 токенов: даже попадание в кэш даёт 2–4 с префилла, а `effortLevel=high` добавляет 10–30 с генерации.
2. Кэш-пинги конкурируют с ходами и/или не успевают между ними.
3. Префикс не совпадает между запросами (клиент дописывает `<system-reminder>` в последнюю реплику).

Диагностика: включить `direct_debug` в `config.json`, поймать `[cache] in/read/write` на двух подряд идущих ходах
одной сессии. `write` размером с историю — префикс рвётся, искать различие в сообщениях; `write` маленький —
время уходит на генерацию, тогда мерить `[ttft]` и снижать effort.
Для сравнения на том же контексте: `transport: "agent"` даёт базовую линию.
