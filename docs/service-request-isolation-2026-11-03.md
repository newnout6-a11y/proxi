# Изоляция служебных запросов и учёт прогрева

Разбор пользовательского лога показал, что семь tool-less вызовов Opus MEDIUM
были внутренними проверками действий Auto mode в Claude SDK. Их собственный
системный промпт имел 195 206 символов. Relay подставлял основной head и 136
инструментов, а системные инструкции классификатора добавлял пользовательским
сообщением после меняющейся команды. Это нарушало роли и вынуждало повторно
записывать большой стабильный блок после изменённого входа.

## Исправления

- Все tool-less запросы direct transport используют отдельную временную сессию.
  Сохраняется аккаунт основного диалога, когда он уже определён; проверка маршрута
  не позволяет незаметно переключиться на другой аккаунт. Контекст, инструменты,
  точки кэширования и idle keepwarm основного чата не наследуются и не изменяются.
- У известных клиентов Claude/OpenCode текстовые вызовы получают собственный
  system перед переменным входом. Relay не читает для них проект и не добавляет
  инструкции локального исполнения. Собственный большой system классификатора
  сохраняется полностью и имеет самостоятельный стабильный cache key.
- Ответ классификатора не запускает shell relay. Пустой служебный ответ не
  переписывается общим coding-промптом повторной попытки. Обычные задачи relay
  сохраняют настроенные project context и локальное исполнение; явно переданные
  инструменты с `tool_choice=none` также сохраняют свой смысл.
- Native Electron Claude Desktop определяется по его user-agent даже без ID
  сессии. `PURPOSE` использует подтверждённые сигнатуры проверок подключения,
  заголовков и Auto mode. Для остальных текстовых вызовов клиента выводится
  `client-text`, без догадки по длине сообщения.
- Проверка подключения с `.` больше не получает тысячи токенов проекта relay.
  `/count_tokens` остаётся локальной приблизительной оценкой, теперь учитывает
  определения инструментов; заголовок `x-proxi-token-count: estimated` сообщает
  предел точности. Локальные запросы отмечены в консоли.
- Фактический `creditsUsed` каждого keepwarm списывается один раз в его рабочем
  потоке, включая отмену ожидания, обрыв и ошибку после получения расходов.
  Повторные metadata одного ping не создают повторное списание. Числа проверяются
  на конечность и неотрицательность; неизвестные расходы не заменяются нулём.
- Общий баланс помечается `UNREPORTED USAGE`, если upstream не сообщил стоимость;
  окончательная сверка требует серверного баланса. При изменении расходов во
  время обновления баланса снимок остаётся stale, без двойного вычитания.
- Фиолетовый цвет модели, effort и стоимости заменён на ANSI bright green (92).
  Бирюзовый read, янтарный write и красные предупреждения о записи сохранены.

## Граница проверки

Регрессии проверяются без платной генерации: реальные parse/runner/pool/build_body,
подменённый поток upstream и локальный HTTP-сервер. Проверяется порядок system /
переменный вход, отдельный cache key, отсутствие чужих tools, неизменность main
head, все режимы сессий, busy/idle affinity и расходы при отмене рабочего потока.
Три прежних теста, требовавших наследования основного head/tools, обновлены на
новый контракт; их запросы теперь завершаются имитатором вместо ошибки настройки.

Эти проверки подтверждают форму исходящего запроса и локальный учёт. Они не
измеряют фактический cache hit или новую стоимость у провайдера. Первый запуск
классификатора по-прежнему отправляет его собственный большой system; результат
повторного чтения кэша нужно оценивать по следующему реальному журналу.

## Выполненные проверки

```text
uv run --python 3.14 --with-requirements requirements.txt --no-project python -m pytest tests -o addopts= -q --tb=short
1095 passed in 133.55s; exit 0

node --test tests/test_opencode_labels.mjs
2 passed, 0 failed; exit 0

git diff --check
exit 0

python scripts/watch_relay.py --demo
exit 0; при FORCE_COLOR=1 / отсутствии NO_COLOR стоимость использует ANSI 92,
read — 36, обычный write — 33, WRITE SPIKE — 1;91
```

Полный прогон вывел `ConnectionAbortedError` из имитатора в тесте намеренного
обрыва сокета (`test_pool_stream_regressions.py`); тест и процесс pytest завершились
успешно. Новых платных запросов для проверки этих исправлений не выполнялось.

В исходном коде целевые регрессии сначала дали 33 failed / 4 passed. Последующий
полный прогон обнаружил три устаревших ожидания наследования head/tools; после их
обновления полный набор прошёл с указанным выше результатом.
