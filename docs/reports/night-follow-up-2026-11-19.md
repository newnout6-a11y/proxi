# Продолжение ночной работы Proxi

Проверяются исходные пункты R2–R6 и новый R7. Для живой проверки сначала нужен
успешный прогон на поддельном upstream, затем отдельный временный relay и короткие
запросы с ограниченным выводом. Записываются коммит, клиент, модель, тип запроса,
время до первого текста и итог. Если доступных настроек для конкретного транспорта
нет, строка матрицы остаётся непроверенной.

Начальный живой контроль для R1: Chat Completions через Minara ответил 200,
первый текст пришёл за 1545 мс. Это подтверждает рабочий путь тестового relay,
но пока не закрывает матрицу остальных форматов или IDE.

## R2: завершение SSE

Сверены документированные признаки конца: [Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)
использует `finish_reason` и маркер `[DONE]`; [Responses](https://developers.openai.com/api/reference/resources/responses/streaming-events)
использует именованные события результата; [Anthropic Messages](https://platform.claude.com/docs/en/build-with-claude/streaming)
заканчивается `message_stop`. На синтетическом upstream каждый из трёх драйверов
ранее выдавал 200 после обрыва. После исправления такой поток возвращает ошибку,
не записывает частичный ответ в историю и не выдаёт накопленный вызов инструмента.

| Живой путь клиента через Minara | HTTP | До первого текста | Всего | Конец |
|---|---:|---:|---:|---|
| Responses | 200 | 1835 мс | 1837 мс | `response.completed` |
| Anthropic Messages | 200 | 1331 мс | 1332 мс | `message_stop` |

Оба запроса к `minara/deepseek-v4-flash` дали ожидаемый ответ. По журналу они
израсходовали 0,003 кредита Minara. Это живые проверки преобразования клиентских
протоколов, а исправление прямых универсальных драйверов подтверждено на заглушках.
На Python 3.14 прошли 70 целевых тестов протоколов и маршрутизации и полный набор:
11 023 прошли, 2 пропущены. Ruff и `git diff --check` прошли.

## R3: таймауты Minara и быстрые кандидаты

`504` и `524` от шлюза Minara превращаются в `upstream_timeout`, а оригинальный
HTTP-статус сохраняется в диагностике. У обрыва может быть списание, поэтому
relay не повторяет генерацию после этих статусов, пустого 503 или SSE-ошибки.
Релею всё ещё разрешено повторить явно распознанный отказ выбора канала; тест
подтверждает закрытие старого ответа и получение результата на следующей попытке.
Синтетический тест с двумя аккаунтами проверяет отсутствие второй отправки на 524.
Живой 524 намеренно не вызывался: его наличие уже видно в прежних трассах.

Контрольный живой запрос: одна и та же короткая арифметическая задача, отдельный
контекст каждого запроса, лимит 64 токена, один аккаунт Minara. Три результата верны.

| Модель | Effort | HTTP | До первого текста | Всего |
|---|---|---:|---:|---:|
| `minara/gpt-6-luna-pro` | low | 200 | 4440 мс | 4441 мс |
| `minara/glm-5.3-flash` | minimal | 200 | 2344 мс | 2347 мс |
| `minara/deepseek-v4-flash` | none | 200 | 1224 мс | 1227 мс |

Журнал суммарно показал 0,0459 кредита Minara. Flash-кандидаты подходят для следующей
проверки коротких служебных ответов. По одному примеру нельзя оценить качество
резюме или память длинной сессии. Рабочие маршруты не менялись; `gpt-5.4-mini`
не включён в эту сопоставимую проверку.

На текущем коде повторил ту же задачу по три раза на модель с отдельным ID
и чередованием порядка. Все девять ответов верны и завершились `stop` / HTTP 200.

| Модель | До первого текста, мс | Медиана, мс |
|---|---|---:|
| `minara/gpt-6-luna-pro`, low | 3296, 4005, 3296 | 3296 |
| `minara/glm-5.3-flash`, minimal | 1946, 1655, 1621 | 1655 |
| `minara/deepseek-v4-flash`, none | 1334, 1097, 1115 | 1115 |

Расход повторов — 0,1374 кредита. `gpt-5.4-mini` отсутствует в каталоге
тестового аккаунта Minara. Три повтора подтверждают разницу на короткой
задаче, но не измеряют редкие задержки.
Проверки: 234 целевых теста и отдельная матрица с двумя аккаунтами, полный набор
на Python 3.14 — 11 029 прошли, 2 пропущены. Ruff и `git diff --check` прошли.

## R4: разделение клиентов

Два разных клиентских ключа и основной ключ больше не попадают в одну ветку при
равных ID диалога или одинаковой выведенной истории. Разделение применяется
к дочернему и родительскому ключам, подбору сохранённой истории, инструментам
Codex и объединению инструментов. Для клиентских ключей режим `shared` сохраняет
отдельный контекст; прежняя общая сессия остаётся только у основного ключа.
У Claude через Minara и OpenRouter relay передаёт отдельный `prompt_cache_key`
на диалог, даже если заголовок и подсказка оператора одинаковы. Первый ход после
перехода может записать новый кэш; поведение внутреннего кэша провайдера этим
ключом не гарантируется.

Живой тест на отдельном relay в режиме `shared`: два параллельных запроса к одной
модели Minara с одинаковым ID диалога и двумя разными ключами дали два 200 и
две отдельные записи пула с разными `thread_id`; общая мастер-сессия осталась
пустой. Расход по журналу — 0,003 кредита. Одинаковую безымянную историю с одним
учётным ключом нельзя отличить от повторной отправки; для гарантированной
изоляции этой ситуации задаётся явный ID либо выключается inference.
Офлайн прошли 196 целевых тестов и полный прогон на Python 3.14: 11 033 прошли,
2 пропущены. Ruff и `git diff --check` прошли.

## R5: структурированная консоль

Режим `RELAY_LOG_FORMAT=jsonl` использует одну схему для новых строк консоли и
`relay.log` супервизора. Маршрут, сессия, TTFT, usage и HTTP-итог связываются
по `request_id`; повтор можно отличить по `turn_id` и `attempt`. В HTTP-итоге
разделены код на проводе и итог потока: при SSE-ошибке HTTP может остаться 200.
Ожидаемые 400 от Claude Code помечаются как ожидаемые и не повышают уровень до
предупреждения. Токены и списания записываются с явными единицами; события
ожидания не участвуют в TTFT. Обычный текстовый режим остаётся по умолчанию.

Живой Responses → Minara: HTTP 200, `response.completed`, первый текст через
1334 мс, задержка до первого события апстрима 1323 мс, один выходной токен,
0,0015 кредита Minara. Все 15 строк stdout разобрались как JSON; проверка не
нашла в них credentials и исходный ID сессии. Изолированный тест супервизора
проверил, что валидная строка relay сохраняет время, а необработанный вывод
дочернего процесса не попадает в файл с сырым содержимым.

Полный прогон: `uv run --offline --python 3.14 --with-requirements requirements.txt python -m pytest -o addopts= -q -n 4 -p no:cacheprovider --tb=short tests`
— 11 037 прошли, 2 пропущены. `uvx --offline ruff@0.15.13 check --no-cache .`
и `git diff --check` прошли. Рабочий relay не перезапускался; формат в нём не переключался.

## R6: установленные клиенты, продолжение сессий и хуки

Каждый клиент запущен с отдельным временным профилем против relay на localhost,
с временным ключом и одним настроенным аккаунтом Minara. Модель одна:
`minara/deepseek-v4-flash`; промпты и файлы синтетические. В профилях были отключены
чужие плагины и повторные отправки там, где CLI это поддерживает. Время первого
текста апстрима берётся из журнала, первый текст клиента — из его JSON-событий
от запуска процесса. У Codex первое текстовое `item.completed` может появляться
после того, как текст уже доступен клиенту; это время до события, а не до буквы в TUI.

| Клиент и команда | Путь | Первый текст upstream, мс | Событие текста CLI, мс | Выход CLI, мс |
|---|---|---:|---:|---:|
| Codex 0.167.0, `codex exec --ephemeral --json` | Responses | 2302 | 3349 | 7949 |
| Claude Code 2.1.322, `claude --bare --print --output-format stream-json --include-partial-messages --verbose` | Messages | 1520 | 5831 | 5918 |
| OpenCode 1.19.3, `opencode run --pure --format json` | Chat | 1420 / 1060 | 6738 | 6927 |
| DeepSeek Harness 0.2.2-alpha.3, `dsh --profile headless --patch <временный файл> --json` | Chat | 1447 | 4351 | 4534 |

Четыре клиента дали ожидаемый текст и код выхода 0. OpenCode и Harness
сделали по два HTTP-запроса; в таблице указаны текстовые начала, видимые в журнале.
Расширенные сценарии:

- `codex exec resume <id>` продолжил ход после синтетического промпта из 40 664
  знаков и автоматического сжатия. Relay увидел `codex.compaction_tools_restored`.
  Сжатие и финальный ход вернули 200, ID в CLI и метка диалога в relay сохранились,
  модель вернула точную фразу из первого хода. Лимит сжатия в тестовом профиле
  задан явно (`model_auto_compact_token_limit=11500`). Отдельно `update_plan`
  прошёл два запроса Responses и дал реальное событие списка задач.
- Claude Code вызвал `Read` для временного файла, локальный `PostToolUse` сработал
  один раз, финал совпал с содержимым файла. Перед двумя успешными запросами
  клиент сам прошёл через три ответа 400; списаний на этих трёх ответах не было.
- `opencode run --command r6probe --file <файл>` в 1.19.3 дошёл до модели без
  содержимого вложения. На локальной заглушке это повторилось, в том числе для
  `@relay-fixture.txt` в шаблоне команды: тело сначала формирует сам CLI, relay
  содержимого ещё не получает. Отдельный `opencode run --pure --format json
  <запрос> --file <файл>` передал текст и в живом прогоне вернул точную строку.
- `dsh --profile headless --patch <файл> --json --session-id <id>` продолжил
  сохранённую сессию и вернул фразу из первого хода. Тестовый плагин через
  `llm-pi-ai/request-headers` передал название и ID в трёх запросах, включая
  запрос названия чата. Relay увидел одну и ту же сессию; сырые ID в JSONL
  отсутствовали. Главные запросы начали писать через 1377 и 1322 мс.
- В браузерном интерфейсе временного `dsh --profile web --patch <файл> --host
  127.0.0.1 --port <свободный порт> --no-open` модель вернула `R6_WEB_OK`, UI
  показал «Завершено». От отправки до появления ответа в браузере прошло около
  3,9 с. Основной запрос занял 2050 мс, первый текст апстрима — 2023 мс. Отдельный
  запрос названия чата также вернул 200. Расход этого прогона — 0,1886 кредита.
- В отдельном headless-профиле включён штатный PTC-исполнитель Harness с
  `read-only` и ограничением времени. Один `run_code` выполнил только
  `241 + 387`, CLI выдал `tool_call`, `tool_result` с `628` и финальный `628`.
  Три запроса вернули 200, включая фоновое название чата; процесс завершился
  за 7430 мс, расход — 0,1927 кредита. Это проверяет обычный цикл PTC;
  восстановление подписанного Retool-кэша после PTC отдельно не проверялось.

В диагностике Codex и Harness изначально не имели поля `client`, хотя слой
промптов их распознавал. Подключил то же распознавание к логам, сохранив
семантику `client_context.request_kind` и ключей диалогов. Повторные живые
прогоны подтвердили метки `codex` и `harness` и в журнале, и в JSONL.
Суммарный расход всех описанных живых проверок R6, включая неудачное вложение,
— 1,7938 кредита Minara. Полный набор на Python 3.14 той же командой, что в R5:
11 040 прошли, 2 пропущены. Ruff и `git diff --check` прошли.

## R7: первичная сверка

Retool [документирует](https://docs.retool.com/org-users/guides/retool-api/authentication)
Bearer-токены организации с явными правами для [API v2](https://docs.retool.com/org-users/concepts/retool-api).
Документация по [Retool AI](https://docs.retool.com/data-sources/reference/ai-models)
отдельно описывает модели для AI-ресурсов и агентов. Это не подтверждает, что Bearer-токен
API v2 подходит для текущего пути Copilot в relay. В исходниках текущего пути есть
версия веб-клиента ([auth.py](../../auth.py#L225)) и поле `requestOrigin: Browser`
([direct.py](../../direct.py#L1215)); они относятся к существующему пути Copilot
с авторизацией веб-сессией. Изменение этих полей само по себе не превращает его
в документированный API.
Для запуска заранее настроенного Workflow Retool [документирует отдельный ключ](https://docs.retool.com/workflows/guides/webhooks)
в заголовке `X-Workflow-Api-Key`. Штатный вариант для автономной интеграции — отдельный
Workflow с нужным AI-действием, ограниченный ключ и явные пределы запросов; у него
свой жизненный цикл и он не гарантирует паритет с Copilot. На этой машине подходящий
Workflow не запускался. Изменения идентификации и обход ограничений провайдера в
проверку не входят.

Нагрузка расходится по разным путям: пользовательская генерация через Copilot
или агентский транспорт; отдельно чтение баланса, обновление каталога и прогрев
кэша. Дефолты в [config.py](../../config.py): баланс — 300 с, чтение в три потока;
каталог Retool — 6 ч, до 10 проверок новых моделей; прогрев — 240 с для подходящих
диалогов. Это значения в коде, а не замер частоты боевых запросов. Если нужен
меньший объём фонового трафика, сначала посчитать его по фазам в журнале и оценить,
сколько даёт прогрев в экономии кэша. Затем можно уменьшать частоту или отключать
ненужные фоновые функции и соблюдать `Retry-After`. Менять рабочие cookies,
идентификацию клиента или настройки продакшна для этой проверки не потребовалось.

## Открытые вопросы и ограничения

- В прежней сторонней трассе остался текущий ключ relay. Ротация потребует синхронно
  обновить клиентские профили. Действительность старых сессий Retool из публичной истории
  не установлена. Эти операции не привязаны к проверке свежего кода.
- Для живой матрицы независимых провайдеров нужны их штатные тестовые учётные данные.
  При исходной сверке список универсальных провайдеров был пуст; публичный каталог
  и успешный ответ другого транспорта не засчитываются как живой прогон.
- Для `gpt-5.4-mini` нет сопоставимого живого замера. Для редких задержек нужна
  более длинная серия, для качества — задачи сложнее короткой арифметики.
- Проверены конкретные инструменты, хуки и продолжения, описанные в R6. Web
  Harness прошёл короткий ход; нативные приложения Desktop, полная матрица `/`
  и `@`, PTC на Retool после возобновления кэша и остальные инструменты остаются
  открытыми. Пользовательские клиентские профили не менялись.
