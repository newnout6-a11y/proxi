## Thinking и уровни мышления

`reasoning_effort` / `reasoning.effort` / Anthropic thinking-настройки
проверяются относительно возможностей выбранной модели. Поддерживаемые уровни
публикуются в каталоге; неизвестные уровни отклоняются, а не заменяются молча.
Выбранный уровень передаётся как `modelProvider.reasoningEffort` в настоящий
кадр Retool `user_prompt`, а не только текстом внутри prompt.

Relay передаёт только текст thinking, который действительно пришёл от
провайдера: Chat `reasoning_content`, Responses reasoning-summary events и
Anthropic thinking blocks. Опрос сохранённой истории дополнен финальным
запросом для коротких ходов; WS/history не дублируются и не смешиваются с
соседними ходами. Очередь thinking обрабатывается и при молчащем WebSocket.
Подпись передаётся только при наличии настоящей подписи upstream.

Живые прямые проверки `RelaySession` с уровнем `high` показали:

| Модель | Ответ | Что сохранил Retool | Что relay мог показать |
| --- | --- | --- | --- |
| Claude Opus 5.5 | Получен текст ответа, завершение без ошибки | `type: thinking`, пустая строка `thinking` и непрозрачная подпись | Текст ответа; видимого текста thinking провайдер не предоставил |
| GPT-5.5 | Получен текст ответа, завершение без ошибки | `type: redacted_thinking`, непрозрачное поле `data`, `responseItemId` | Текст ответа; plaintext thinking отсутствует |

В обоих случаях сообщения имели корректные `createdAt` после отправки
prompt. Это не потеря текста фильтром времени. Retool может скрывать reasoning
или выдавать лишь защищённый блок. Relay не расшифровывает такие блоки, не
сочиняет ход мыслей и не выдаёт provider-specific opaque data за совместимый
OpenAI `encrypted_content`. Наличие настроенного уровня мышления не обещает
доступ к скрытому рассуждению модели.

## Ключ, инструменты и проектный контекст

Один relay key принимается в OpenAI Bearer и Anthropic `x-api-key` заголовках;
он не привязан к OpenCode. Реализованы контракты Chat Completions,
[Responses](https://platform.openai.com/docs/api-reference/responses) и
[Anthropic Messages](https://docs.anthropic.com/en/api/messages).
Responses поддерживает function/custom tools и согласованный lifecycle SSE;
Anthropic — tool-use/tool-result и thinking/text blocks.

При наличии инструментов клиента relay передаёт ему вызовы объявленных tools
и использует возвращённые результаты. Внутренние инструменты sandbox Retool
не выдаются за инструменты клиента. Инструкции и рабочая директория клиента
описывают его проект; локальный проект хоста relay не подменяет этот контекст.
Без инструментов клиента используется настроенный `workspace_root`, его
документы и отдельный механизм локального выполнения с выбранной policy.
Контекст, тестовый вывод и реальные операции с файлами проверяются отдельно
от заявления модели о выполненной работе.

API-совместимость и проверка синтетическими tool-result циклами сами по себе
не доказывают полную совместимость каждой версии Codex, Claude Code или
другого клиента. Результаты отдельных живых CLI-проверок нужно указывать
отдельно от offline harness.

## Проверка искусственных задержек транспорта

Транспорт проверен отдельно от времени генерации модели. Обнаружены и
устранены три ожидания, не требовавшиеся успешному запросу:

- После открытия каждого нового WebSocket relay ждал 400 мс тишины,
  предварительно читая стартовые служебные кадры. В измеренном образце
  `open()` занял 6,405 с, из них 0,413 с приходилось на этот drain. Теперь
  prompt отправляется после handshake, а служебные кадры обрабатываются
  обычным receive loop. Закрытие незавершённых старых сокетов сохранено.
- После получения credits до конца хода relay всё равно ожидал ещё один
  trailing-кадр до 250 мс. Когда credits уже получены, повторное ожидание
  исключено. Если credits ещё не пришли, ожидание сохранено: учёт расхода
  нельзя заменить фоновым действием и объявить запрос полностью проверенным.
- После последней неудачной HTTP-попытки выполнялся backoff, хотя следующего
  retry уже не было. Последний бесполезный sleep удалён; паузы между реальными
  повторными попытками после сетевой ошибки, 5xx и rate limit сохранены.

Пустые REST-проверки истории раньше продолжались каждые 2 с независимо от
результата. Теперь при отсутствии новых thinking/tool данных интервалы
составляют 2, 4, 8, затем максимум 15 с. Новое содержимое возвращает обычную
частоту, WebSocket activity сбрасывает backoff, а при завершении хода
выполняется финальная проверка истории. Relay не отключает thinking навсегда
из-за одного скрытого/пустого ответа модели и не создаёт дополнительную
глобальную очередь искусственного ограничения запросов.

После изменения выполнен один живой запрос GPT-6 Sol (`low`): получен ответ
`OK` и настоящий credits event, prompt отправлен через **0,157 мс после
handshake**, за ход выполнено **3 HTTP-запроса истории**. Полное время —
**23,246 с**. Это подтверждает работоспособность нового порядка обработки,
но один запрос не доказывает ускорение генерации провайдера или постоянное
снижение полного времени ответа на указанную величину.

Повторная живая проверка баланса вернула HTTP 200, но rate-limit заголовков
не содержала. Указанные в старом `PROTOCOL.md` 120 запросов/минуту остаются
историческим наблюдением, а не заново подтверждённой квотой аккаунта.

`recv_timeout` задаёт интервал ожидания сокета и не обрывает генерацию сам по
себе; фактический предел хода задаёт `turn_timeout`. Ограничения сетевого
handshake, сбор credits, завершение poller и закрытие незавершённых сокетов
не удалялись. Паузы `Refresher` относятся к восстановлению авторизации и не
задерживают здоровые модельные запросы.

## Повторный прогрев на каждом шаге IDE

Нативный веб-клиент Retool изучен по актуальным публичным JS и отдельному
тестовому диалогу. Он прогревает sandbox при открытии, сохраняет WebSocket,
постоянно отвечает на ping/ACK и отправляет следующий prompt в готовое
соединение. В установленном Harness уникальный session ID доходил до SDK,
но выключенный и скрытый adapter flag не позволял отправить affinity header.
Поэтому relay создавал новый thread и соединение на каждый HTTP-запрос.

В Harness локально исправлены schema/type/gate существующего
`sendSessionAffinityHeaders`, настройка включена только для Retool. Основной
агент и субагенты используют собственные ID; общий постоянный ID не добавлен.
Эта внешняя правка проверена отдельно: 167 source-тестов, typecheck/build и
семь localhost mock-запросов установленной сборки. Исходный checkout Harness
сохранил все девять ранее существовавших правок; новая правка закоммичена
отдельно локально и не входит в diff этого PR.

Relay получил постоянный ограниченный WS reader для idle control traffic и
точное переиспользование клиентского контекста. Список SHA256 fingerprint-ов
неизменённых сообщений должен строго расшириться; тогда передаётся новый
суффикс истории. Изменение последнего сообщения, compaction, смена инструкций
или tools и предыдущая неудача приводят к свежему thread с полным контекстом.
Отмена завершается до освобождения lease. Неанонимные диалоги изолированы;
анонимные запросы сохраняют свежие независимые thread.

Финальный живой замер установленным адаптером Harness, Opus 5.5 и прежним
`max`, два коротких запроса с объявленным инструментом без его выполнения:

| Показатель | Первый запрос | Следующий запрос |
| --- | --- | --- |
| Первый текст | 19,329 с | 1,406 с |
| Полное завершение | 20,148 с | 2,182 с |
| Отправленный prompt | 1790 символов | 392 символа |

На оба запроса пришлись ровно одно создание thread, один start и один connect.
Это доказывает отсутствие повторного cold setup и полной пересылки истории в
проверенном цикле. Большой проектный контекст и работа инструментов могут
занимать больше времени. Ускорение самих вычислений модели и ответ за одну
секунду для произвольной задачи не заявляются. Оценки tokens остаются
приблизительными; счётчик не использовался для этого сравнения.

Проверки выполнены на изолированной копии будущего commit без приостановленной

## Реальный цикл Harness и Claude Code

Проверка двух маленьких запросов выше не покрывала полный цикл IDE.
В реальном Harness с 73064 символами system и Opus 5.5 `max` сохранённые
запросы заняли 35,836 и 27,952 с, до первого текста — 32,460 и 25,466 с.
Между ними Harness запускал генерацию заголовка с тем же session ID, но без
инструментов. Этот запрос попадал в основной thread и помечал его контекст
негодным; следующий основной ход создавал новый thread. System и tools двух
основных запросов совпадали. Причина подтверждена точным SHA256 system title-job
в сохранённом Harness запросе и в соответствующем Retool сообщении.

Исправления:

- Tool-less запросы отделены от native-tools диалога по клиентскому ID и
  system fingerprint. В shared mode они получают изолированный lease.
- Claude Code session ID извлекается из JSON-строки `metadata.user_id`;
  account/device/parent IDs не используются вместо собственного ID разговора.
- Fingerprints сравнивают model-visible содержимое с сохранением границ
  сообщений; перемещение SDK cache markers не создаёт ложного редактирования.
  Правки настоящего текста, tool IDs/results и параметров по-прежнему сбрасывают
  контекст. Новых догадок по User-Agent или тексту задания нет.

Реплей сохранённых запросов через установленный Harness adapter с параллельным
title-job, без исполнения project tools и с прежним Opus 5.5 `max`:

| Показатель | Первый основной запрос | Следующий основной запрос |
| --- | --- | --- |
| До первого текста | 28,519 с | 4,906 с |
| Завершение | 30,450 с | 7,107 с |
| WS prompt | 80960 символов | 902 символа |

На три запроса пришлись два thread/start/connect: один для основного диалога,
один для title-job. Это изолированный реплей реальных client payloads с
сохранённым предыдущим assistant message, а не полная автоматизация GUI.
Локальные execution/project injection для диагностического сервера были
выключены; исходный клиентский system сохранён. Время первой холодной операции
остаётся значительным, постоянные 1,4/2,2 с для IDE не заявляются.
