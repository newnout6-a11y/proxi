# Единый пул моделей Retool и Minara

Retool и Minara могут обслуживать **одно привычное имя модели**. Клиент выбирает,
например, `claude-opus-5-5`, а relay подбирает совместимый маршрут конкретного
аккаунта. Отдельный пункт `minara/...` для этого не нужен. Подключение Bearer,
ограничения транспорта и учёт стоимости описаны в [Minara](minara.md).

## Один публичный ID, разные upstream ID

В записи Minara в `accounts[]` добавьте `public_id` к описанию модели:

```json
{
  "upstream": "minara",
  "base": "https://api.minara.ai/v1",
  "bearer_token_env": "MINARA_TOKEN",
  "minara_models": [
    {
      "id": "anthropic/claude-opus-5.5",
      "public_id": "claude-opus-5-5",
      "provider": "anthropic",
      "tools": true,
      "forced_tool_choice": false,
      "reasoning": true,
      "reasoning_effort_levels": ["high"]
    }
  ]
}
```

Это фрагмент аккаунта, не замена полной конфигурации. Значения capabilities —
явное описание проверенного оператором маршрута, **не** обещание, что все модели
Minara имеют такие возможности. Не добавляйте уровни или limits по аналогии с
одноимённым Retool-маршрутом. Точный upstream ID берётся из каталога Minara;
`public_id` задаёт соответствие существующему клиентскому имени явно.

- `id` — что relay отправляет API Minara.
- `public_id` — что видит и выбирает клиент. Каталог публикует его один раз.
- Обычный Retool ID и его поддержанный provider-prefix alias продолжают работать.
- Старое явное имя `minara/<id>` остаётся совместимым alias для диагностики и
  прежних клиентов, но не создаёт дополнительный опубликованный слот mapped-модели.
- Без `public_id` действует прежний отдельный маршрут `minara/<id>`.

Нельзя объединять разные модели только ради одинакового имени. Оператор отвечает
за соответствие версии/семейства; relay не превращает одну модель в другую.

## Как выбирается аккаунт

Перед отправкой проверяются возможности **конкретного маршрута**, а не только
публичная карточка модели: tools, изображения, явный effort, verbosity, output
limit и принудительный tool choice. Маршрут, который не может выполнить запрос,
не становится кандидатом. Неподдерживаемый контроль не должен молча понижаться;
существующие явно включённые настройки совместимости сохраняют своё значение.

`forced_tool_choice: false` означает, что нативный `required` или выбор имени
инструмента не направляется на этот Minara-маршрут. `auto` с tools остаётся
допустимым, если `tools: true`. Retool-специфичные обходы применяются только после
выбора Retool, а не автоматически ко всем моделям того же семейства.

Для нового диалога сначала действует операторский `priority` (меньше — раньше).
При равном приоритете доступные провайдеры делят новые диалоги по нагрузке и
round-robin, затем выбирается аккаунт выбранного провайдера. Поэтому один аккаунт
Minara не теряется за двумя десятками Retool-аккаунтов. Это не обещание точного
процентного распределения при неравной нагрузке, ограничениях и отказах.

## Главный диалог и субагенты

Диалог сохраняет привязку к выбранному аккаунту, пока аккаунт может обслуживать
его запрос. Следующий tool-result и обычное продолжение не выбирают нового
провайдера только потому, что нагрузка изменилась.

Субагент с **собственным conversation ID** выбирает маршрут независимо. Например:

1. Главный диалог работает через Retool.
2. Новый субагент с другим ID получает Minara под тем же публичным именем модели.
3. Его tool-result возвращается в тот же Minara-диалог.
4. Главный диалог продолжает свою Retool-историю.

Связь `parent_key` защищает существующее состояние родителя от вытеснения, но не
заставляет ребёнка наследовать его аккаунт. Если клиент выдаёт всем агентам один
и тот же conversation ID, relay не может надёжно угадать независимые диалоги:
важны корректные session/subagent идентификаторы клиента.

## История, перезапуск и границы кэша

При включённом `conversation_state` сохраняется привязка аккаунта и фактического
маршрута. Minara получает binding-only запись даже без подписанных веток Retool:
сохранённая привязка **не** означает сохранённый KV-cache. После штатного
перезапуска тот же диалог возвращается к прежнему доступному аккаунту; смена
приоритета сама по себе его не переносит.

Клиентские сообщения, tool IDs/results и изображения передаются в каноническом
виде. Подписанные thinking-блоки, cache keys и warm-state Retool не переносятся в
Minara. Даже `account_move_keeps_history: true` не разрешает перенос между
провайдерами. Изменение upstream/base/model mapping под тем же публичным ID
инвалидирует несовместимое транспортное состояние.

**Общий KV-cache между Retool и Minara не гарантируется и не создаётся relay.**
Кэш принадлежит upstream. Relay сохраняет affinity, system/tools/effort и историю
настолько стабильно, насколько позволяет запрос клиента, чтобы не вызывать
лишних холодных переходов. При необходимой смене провайдера передаётся полная
каноническая история, но новый провайдер может заново обработать префикс.
Minara не получает Retool keepwarm, refresh или balance-запросы.

Если клиент не прислал прежнюю историю после потери собственной сессии, одна
binding-only запись не восстанавливает отсутствующую переписку. Настройки TTL,
лимитов state и отключение сохранения также ограничивают срок affinity.

## Админка и эксплуатация

Наличие поддержки в коде само по себе не добавляет аккаунт. В рабочей
конфигурации должна существовать отдельная запись Minara с действующим Bearer
или доступной процессу переменной окружения. После сохранения нового аккаунта
текущий admin API отмечает его `pending` до перезапуска relay.

В админке остаются отдельные аккаунты и их upstream, но клиентский каталог
mapped-моделей общий. Это разные уровни: аккаунты нужны для здоровья, приоритета
и стоимости, а публичный слот модели — для выбора клиентом. Цена Minara не
складывается с Retool credits; неизвестный баланс не считается нулём.

Не заменяйте рабочий `config.json` целиком примером. Сохраните существующие
Retool-аккаунты, роли, prompts, state directory и локальный ключ relay. Новый
Bearer не должен попадать в Git или клиентские настройки: клиент использует
локальный ключ relay, а не ключ upstream.
